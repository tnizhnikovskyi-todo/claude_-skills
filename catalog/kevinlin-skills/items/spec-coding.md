# spec-coding

- **Тип:** скилл · **Источник:** https://github.com/kevinlin/skills/tree/main/spec-coding · v1.0.1
- **Вердикт:** **отклонить** (2 мелкие идеи — в заметки)

## Что делает

Разработка по спеке в 5 стадиях: подтверждение цели → `requirements.md`
(user story + EARS: WHEN/WHERE/IF…THEN/SHALL) → `design.md` (обзор,
архитектура, интерфейсы, модели данных, ошибки, тесты, Mermaid) →
`tasks.md` (чекбоксы со ссылками на требования) → выполнение **по одной
задаче** с остановкой на ревью. Явное одобрение между стадиями. Всё в
`docs/specs/<feature>/`. 229 строк, без скриптов, 7 eval-кейсов с ассертами.

## Сравнение с `odoo19-mvp-build:spec-writer` / `odoo-spec-writer`

| Аспект | `spec-coding` | наш |
|---|---|---|
| Источник требований | **Сам пишет черновик** из разговора («сначала черновик, потом вопросы») | Только из одобренного ТР; без ТР отправляет в цепочку `tr-*`; требования не выдумывает |
| Формат критериев | EARS | Given/When/Then (`tr-usecases-acceptance`), ID `AC-01` сохраняются дословно |
| Дизайн | Общий, под любой стек | `tr-odoo-tech-design` + `architecture`, сверка с документацией Odoo 19 |
| Выполнение | По одной задаче, стоп после каждой | `build-allocator` → `scaffolding`/`code-dev` → `testing` → `pr-review` с гейтами |
| Возобновление | По наличию файлов (`tasks.md` с открытыми чекбоксами → стадия 5) | не знаем |

**Вывод:** наша цепочка строже и под домен. `spec-coding` ломает главный
инвариант (ТР — единственный источник) и дублирует `interview-me`
(уточнение цели). Брать как есть нельзя.

## Мелкие идеи

- **Вопрос о статусе — не команда.** «Что дальше?» → назвать следующую
  задачу и спросить, выполнять ли; файлы не трогать. Есть eval
  `question-without-execution`. Стоит проверить, как ведут себя наши
  `code-dev` / `track-convergence`.
- **Возобновление по файлам:** определить стадию по тому, какие артефакты
  уже есть. Для `odoo19-mvp-build` это есть ли SPEC, архитектура, план
  распределения.
