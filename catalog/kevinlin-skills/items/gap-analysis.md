# gap-analysis

- **Тип:** скилл · **Источник:** https://github.com/kevinlin/skills/tree/main/gap-analysis
- **Версия:** `metadata.version 1.1.0` в SKILL.md (в `versions.json` указано 1.0.0, рассинхрон) · коммит `0d3e083b9a714db97eb733327ef5066efaf1451b` · MIT
- **Вердикт:** **адаптировать**: конвенции, а не HTML-шаблоны

## Что делает

Сравнивает документы требований (BPMN, FeatureSpec, RFP, детальные
требования) и выдаёт **самодостаточный HTML** с переключателем темы:
таблицу разрывов с severity, пилюлями воркстрима/владельца и тремя
блоками «совпало / неявно / не хватает». Три режима: A — новый отчёт,
A2 — точечное обновление существующего, B — мастер-реестр по всем отчётам
(группировка по категориям, табло, фильтры).

## Как устроен

- `SKILL.md` (154 строки): маршрутизация A / A2 / B, обязательные входы,
  шаги, «что значит хорошо».
- `references/conventions.md` (172): severity, **дерево выбора префикса ID**,
  пилюли, владельцы, глоссарий, провенанс, связь строки и блока.
- `references/individual-report.md` (250), `register.md` (188): анатомия HTML.
- `assets/*.template.html` (~1100 строк): готовые шаблоны с CSS/JS.
- `evals/evals.json`: 3+ кейса с текстовыми ассертами.
- Скриптов нет, сети нет.

## Что ценного (переносимо)

1. **Обязательные входы спрашиваются один раз и явно:** папка вывода и
   **файл глоссария**. Без глоссария любое расхождение терминов помечается
   `AMB-`, в начале отчёта пишется предупреждение.
2. **Префикс ID по типу находки, а не по файлу.** Дерево по частоте:
   `BPM-` дефект модели процесса → `MFR-` в спеке P0/P1, а требования нет →
   `CTR-` два документа противоречат → `AMB-` термин двусмысленный → …
   → `D-` открытое решение клиента → `G-` по умолчанию, а не первым выбором.
3. **ID никогда не перенумеровываются.** Новые идут в конец; решённые
   получают `Resolved` и остаются в таблице, потому что на ID ссылаются
   открытые вопросы и сводки.
4. **Провенанс как тройка:** цитата источника (FR-id, §RFP, id задачи BPMN)
   + одно предложение «почему важно» для читателя-бизнеса + владелец,
   который единственный может решить. Нет любой части — строка не готова.
5. **Severity защищается одним предложением;** не можешь написать — severity
   неверная. Разделять **блокер** («подрядчик не начнёт без ответа») и
   **замечание** («аудит слабее идеала»).
6. **Противоречия не сглаживать:** приводить оба варианта дословно
   («RFP §5: 1200 пользователей; NFR-P02: 200 — расхождение в 6 раз»).
7. **Замыкание на вопросы:** каждый Critical/High должен иметь пару в
   файле открытых вопросов.
8. **Узкий режим обновления (A2):** читать только сам отчёт, источники
   не перечитывать, менять только строку и связанный пункт, обновить дату,
   больше ничего не «улучшать».
9. Мастер-реестр: дедупликация одинаковых разрывов из разных отчётов с
   каноническим ID и перекрёстными ссылками.

## Что не подходит

- Весь текст привязан к одному тендеру (WS1–WS7, BSC/Zühlke, SAP VA01/VK11,
  JARVIS, японское регулирование APPI/J-SOX/PMDA). Копировать нельзя, только
  переписывать.
- HTML-формат и переключатель темы нам не нужны: у нас Markdown-журнал и
  `.docx` для клиента. Большая часть объёма (шаблоны, анатомия, правила
  классов CSS) уходит на HTML.
- Закрытый список префиксов из 14 штук тяжеловат; нам хватит 6–7.

## Сравнение с `odoo19-discovery-closeout:discovery-gap-analyzer`

Текст нашего скилла в контейнере недоступен. По описаниям и карте
`proposals/siblings-checked.md`: он стоит после `discovery-scope-mapper`,
читает `журнал_дискавері_*.md` (реестры D/X/C/T/Q/A-N) и `scope_*`, пишет
`gap-аналіз_*`, его читают `discovery-report-builder`, `discovery-sow-builder`,
`journal-to-tr-builder`.

| Аспект | `gap-analysis` | наш (по описанию) | Что делать |
|---|---|---|---|
| Вход | RFP/BPMN/FR-документы | журнал дискавери + scope (наш вход богаче, есть решения D-N) | — |
| Префиксы по типу находки | 14, с деревом выбора | не знаем | **проверить**; предложить 6–7: `MFR-` (процесс клиента есть, требования нет), `CTR-` (сессии противоречат), `AMB-` (термин), `STD-` (стандарт Odoo 19 не покрывает → доработка), `INT-` (интеграция без спецификации), `D-` (решение клиента), `G-` |
| Не перенумеровывать, Resolved вместо удаления | есть | не знаем | **проверить**, важно: на ID ссылаются SOW и ТР |
| Провенанс-тройка | есть | вероятно, ссылки на D/Q-N | добавить «почему важно» и владельца (Клієнт / ToDo / спільно) |
| Глоссарий / AMB- | обязателен | не знаем | в дискавери терминология клиента — частый источник ошибок |
| Critical/High → открытый вопрос Q-N | есть | реестр Q-N уже есть в журнале | правило замыкания: каждый High без Q-N — дефект |
| Режим точечного обновления | есть (A2) | не знаем | добавить |
| Сводный реестр по проектам | есть (B) | нет | не нужно: у нас один журнал на клиента |

## Предложение

Не новый скилл, а вставка в `discovery-gap-analyzer` по образцу
`proposals/odoo19-discovery/`: `proposals/odoo19-discovery/gap/INSERT.md`
+ `references/gap-conventions.md` (~80 строк, переписано под Odoo 19 и
украинский), атрибуция MIT в `references/ATTRIBUTION.md`. A/B на фикстурах
`proposals/odoo19-discovery/tests/fixtures/` (журнал «Смачна Пекарня») с
ключом заложенных разрывов: противоречие сессий, термин клиента, процесс
без требования. Предварительно нужен текущий текст скилла.
