# Модель доступа клиента `mcp-server-odoo`

- **Файлы:** `mcp_server_odoo/access_control.py@64b52df` (862 стр.),
  `mcp_server_odoo/tools.py@64b52df` (4935 стр.), `field_security.py`, `config.py`
- **Лицензия:** MPL-2.0 (берём идеи своими словами)
- **Оценка для нас:** самое ценное в репозитории; приёмник — T3 / `odoo-connector`

## Как устроено

1. **Режим** из `ODOO_YOLO`: `off` (стандарт, нужен модуль), `read`, `true`.
   В стандарте RPC идёт на `/mcp/xmlrpc/common|object` модуля
   (`config.py:200–206`), а не на `/xmlrpc/2/*` ядра — модуль проверяет
   каждый вызов сам.
2. **Клиентская проверка** перед каждым вызовом: `GET /mcp/models/{model}/access`
   → `{enabled, operations: {read, write, create, unlink}}`, кеш 5 мин
   (`access_control.py:102–106, 407–468`). Отказ модуля всегда сразу, выдача
   права — до 5 мин задержки.
3. **Три исхода** проверки: разрешено / отказ / «не удалось проверить»
   (`AccessControlUnavailableError`) — третий тоже не пускает, но
   сообщается как ошибка связи, а не как «нет прав». Полезное различие для
   агента: он не начинает «обходить» права, когда упала сеть.
4. **Связанные модели:**
   - x2many-команды в `values` → операция на связанной модели (`tools.py:185`);
   - пути в домене/`order`/`groupby` → read на каждой модели пути
     (`access_control.py:755–850`);
   - домен с «висящим» `|`/`&` → ошибка (`check_domain_balance`, `:586`),
     иначе приписанный фильтр области вложений сливался бы через OR;
   - вложения/сообщения/активности → право write/read на документе-владельце.
5. **Лимиты:** `create_records`/`update_records` ≤ 100, атомарно; `delete_record`
   — один id; чтение ≤ `ODOO_MCP_MAX_LIMIT` (100); id в диапазоне int32.
6. **Секреты:** поля с последним сегментом имени `password/pass/secret/token/
   apikey/pin/otp/salt…` убираются из «умного» и `__all__`-чтения; явно
   названное поле отдаётся (настоящая граница — `groups=` у поля в Odoo).
7. **`call_model_method`:** только YOLO `true` + отдельный флаг; блок-лист
   моделей и имён (см. README карточки).

## Чего нет

- Подтверждения человеком, preview/diff, dry-run.
- Локального аудита изменений (только лог процесса; аудит — в модуле).
- Нескольких баз в одном процессе.

## Что переносим в `odoo-connector` (своими словами)

- Файл политики: `model: {read, write, create, unlink, methods: [..]}`, всё
  прочее — отказ; рядом с allowlist `model.method` (идея erpipe).
- Проверку x2many-команд и путей домена по той же политике.
- `unlink` — максимум N id (у нас предложить 1 или с подтверждением ≤ 10).
- Блок-лист `_validate_method_call` как второй рубеж в `odoo_execute`.
- Различие «отказ» / «не смог проверить» в тексте ошибки.
