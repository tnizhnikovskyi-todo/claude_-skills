## Что проверили по коду (а не по README)

1. **Критерий «оставить/откатить» (текущий, v2.1, PR #13):** N=3 свежих
   судьи-субагента, каждый в ОДНОМ вызове читает старую (`git show HEAD:…`)
   и новую версию `SKILL.md`, сравнивает по 9-мерной рубрике и голосует
   better/worse/tie. `cur >= wor` → keep (ничья тоже keep), иначе
   `git revert`. Абсолютные баллы — только для сортировки «кого чинить
   первым» (автор сам замерил шум ±8 баллов у одного и того же текста).
2. **Важно:** в шаге keep/revert судьи сравнивают ТЕКСТ скилла по рубрике,
   тестовые промпты заново не прогоняются. Поведение (dim8, «実测») мерится
   только в Phase 1 (с/без скилла, 2–3 промпта) и опционально в Phase 2.5.
   README называет это «validation-gated, как SkillOpt», но отложенной
   выборки нет — заимствовано название, не механизм (принцип №24).
3. **Защита от переобучения на тестах:** отдельной нет. 2–3 тест-промпта
   пишет тот же агент (happy path + один сложный), показывает человеку.
   Отложенных кейсов нет. Косвенно: одна правка = одно измерение за раунд,
   свежие судьи каждый раунд, человек на чекпоинте после каждого скилла.
4. **Защита от раздувания:** (а) отказ коммитить, если `SKILL.md` > 150%
   исходного; (б) запрет «добавлять воду ради балла» в чёрном списке;
   (в) стоп, если 2 раунда подряд Δ < 2 балла / оба «slight или tie»;
   (г) нельзя добавлять новые файлы в `references/`/`scripts/`.
   Но сама рубрика награждает рост: таблицы отказов, чёрные списки,
   🔴-маркеры. Пример автора (HL-2): +23 строки таблиц fallback дали
   dim3 6.5 → 10. Ничья = keep → дрейф к накоплению.
5. **Честность автора:** признано, что ранние 40 записей дали 0 откатов
   при 67% «dry_run» (мысленный прогон вместо реального), то есть рубрика
   была слишком мягкой. Это хорошее внешнее подтверждение нашего правила
   «без A/B не сливать» (ср. SkillOpt: 0.554 → 0.026 без гейта).
6. **Самоссылочный ложный срабат линта** (коммит `73dc115`, PR #26):
   grep-проверка «красных» слов срабатывала на сам скилл, где эти слова
   приводятся как пример → вечный P0. Решение: читать контекст попадания,
   цитаты/примеры/описание правила = false positive.

## Права, сеть, что ставится

- Установка: `npx skills add alchaincyf/darwin-skill` (сторонний
  установщик) или zip с R2-бакета автора (не проверяемо); ручной вариант —
  положить `SKILL.md` в `~/.claude/skills/darwin-skill/`.
- Действия по инструкции `SKILL.md`: создать ветку
  `auto-optimize/YYYYMMDD-HHMM`, коммитить правки чужих `SKILL.md`,
  `git revert`, `git stash`; писать `test-prompts.json` в каталог КАЖДОГО
  целевого скилла и `results.tsv` в каталог darwin. `rm` и `reset --hard`
  явно запрещены. Сканирует `.claude/skills/*/SKILL.md` (наши скиллы лежат
  в `plugins/boost/skills/` — не найдёт без указания).
- Сеть: «тихая» проверка версии раз в 30 дней — `git ls-remote origin HEAD`
  из каталога скилла и запись `.last-update-check`; обновление не ставит
  само. Карточка результата: Playwright (`npm root -g` через `execSync`,
  фолбэк `npx playwright screenshot`), `xdg-open`/`open`; шаблоны тянут
  Google Fonts. Телеметрии нет.
- Триггер: длинное описание (737 символов), китайские фразы, включая
  широкие («skill怎么样», «帮我改改skill», «skill review»).
- Runtime-neutrality gate: требует вычищать упоминания Claude Code из
  скиллов — для нас вредно (наш плагин сознательно под Claude Code).

## Сравнение с нашим

См. таблицу в `README.md`. Кратко: наш цикл (`skill-feedback` →
`observations/` → еженедельное ревью → ветка `build/fix-*` → A/B
`claude plugin eval` до слияния) сильнее по источнику сигнала (реальные
поправки, а не синтетические промпты) и по критерию (поведение по
грейдерам, а не текст по рубрике). Сверх нашего у darwin: парное
сравнение версий одним судьёй, лимит роста, стоп по убывающей отдаче,
пометка «мысленный прогон», урок про самоссылочный линт.

Найденная у нас слабость: `weekly-review.md` §5 велит «сравнить с прошлым
результатом скилла (отчёт `reports/<slug>.md`)» — это сравнение
абсолютных чисел из разных прогонов, ровно антипаттерн 1b darwin
(у них шум ±8 из 100; у нас на 3 прогонах тоже есть разброс).

## Дешёвые проверки у себя

- Линт «размытых слов» (аналог dim5: «по ситуации», «при необходимости»,
  «можно рассмотреть», «рекомендуется», «по возможности», «на усмотрение»,
  «если уместно») по 8 `SKILL.md` плагина `boost`: **0 попаданий**.
  Как барьер сейчас бесполезен — не берём.
- A/B самого darwin не делали: это метод для человека в цикле, а его
  критерий (голос по тексту) мы и так не примем. Разрешения пользователя
  на запуск чужих скриптов не было и не требовалось.

## Стоимость цикла (оценка, не замер)

- Загрузка скилла ~9–10k токенов (+ ~3k references).
- Phase 1 на скилл: 2–3 промпта × 2 плеча = 4–6 субагентов (~20–50k
  токенов каждый) → ~0.1–0.3M.
- Phase 2 на раунд: 3 судьи × (рубрика + 2 версии скилла) ≈ 3 × 15–25k;
  до 3 раундов → ~0.15–0.25M. Плюс чекпоинты с человеком.
- Итого ~0.3–0.5M токенов на скилл, порядка нашего A/B ($5.5 на 4 кейса
  × 3 × 2 с судьёй sonnet), но мерит в основном текст, а не поведение.

## Открытые вопросы

- Умеет ли `claude plugin eval` парного судью (видит оба ответа в одном
  вызове)? По `evals/README.md` грейдер `llm` судит один прогон. Значит,
  парное сравнение у нас — либо обе версии плагина в одной серии прогонов
  с тем же судьёй, либо отдельный шаг над сохранёнными выводами
  (`--keep-temp`/`--json`). Проверить при реализации T14.
- Порог «роста» для правки: у darwin 150%, у нас лимит `SKILL.md` ~150
  строк уже есть; предложено своё число (+15 строк / +20% за ревью) —
  решает главная сессия.
