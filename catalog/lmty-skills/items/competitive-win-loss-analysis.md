## Что делает

Объясняет повторяющиеся исходы сделок (не одну сделку) по словам клиента,
а не по «фольклору» продавцов. 11 шагов: когорта и окно → нормализация
имён конкурентов и исходов → две колонки причин → коды критериев →
счёт с исключениями → сегменты при достаточной выборке → связь с
изменениями рынка только при верной хронологии → где лежит вес
(продукт, позиционирование, продажи, цена, внедрение, доверие,
инкумбент) → маркировка выборки → гипотезы с тестами → артефакт.

## Ценные правила (переносить)

- **Две колонки, никогда не сливать:** «клиент сказал» (источник, дата)
  и «продавец записал». Сделка только с версией продавца = причина
  неизвестна. Расхождение колонок — обычно и есть находка.
- **«Цена» — главный фольклор.** Каждую «цену» проверять по словам
  клиента; обычно там привычка, инкумбент, невыявленное требование,
  незаконченная проверка безопасности.
- **Знаменатель — сделки со словами клиента.** Сделки «только CRM» не
  голосуют. «Паттерн — это счёт с исключениями; без исключений — это
  история».
- **Не сплющивать механизм:** три «привычки» могут быть тремя разными
  причинами (бумаги по безопасности уже есть, команда обучена, комплаенс
  доверяет инкумбенту) с тремя разными ответами.
- **Порог сегмента** 4–5 сделок с доказательствами на корзину, порог
  называть явно.
- **Хронология:** событие рынка объясняет сделку, только если оно было
  ДО решения И клиент его упомянул.
- **Смещения:** кого интервьюировали (только проигрыши?), кто
  интервьюировал (вендор → клиент смягчает), кто отвечал (чемпион или
  ЛПР), когда (через недели — это память о решении).
- **No decision ≠ проигрыш конкуренту** — отдельная корзина.
- **Гипотеза без теста — это убеждение.**
- Приватность: цитаты по роли, а не по имени; суммы только где нужны.
- Одна сделка анализируется как одна сделка и так и подписывается.

## Отличия от нашего `loss-pattern-analyzer`

Сверено по тексту `sale_todo_claude@2a7f7c1`,
`plugins/odoo19-sales-offer/skills/loss-pattern-analyzer/SKILL.md`.

**Уже есть у нас (и часто сильнее):** метка причины = гипотеза продавца,
«підтверджено чатером» в каждом паттерне; отсев гигиены лидов (аналог
no-decision); проверка «цена без стадии `Proposition` = клиент цифру не
видел»; `Postponed` отдельно; < 10 карточек — паттернов нет, паттерн
≥ 3; раздел «Чого ця вибірка не показує»; роль вместо имени; одна
проверяемое действие на паттерн; порядок по сумме под риском.

**Чего у нас нет (берём):**
1. **Автор фразы в чатере.** Читаем `mail.message` только по `date`,
   `body` — внутренняя заметка продавца засчитается как «слова клиента».
   Нужно различать письмо клиента и log note (поля `author_id`,
   `message_type`, `subtype_id` — проверить на живой базе).
2. **Победы как контрольная группа** той же отрасли и периода: без них
   не видно, что отличает проигрыш (стадия, размер, конкурент).
3. **Исключения рядом с паттерном** и отказ сливать разные механизмы
   под одной меткой.

Не берём: changelog LMTY, CRM-поле competitor (у нас конкуренты только
из чатера), «гипотезы с тестом» вместо действия — наше «одна
перевірювана дія» уже это покрывает.
