# requirement-engineer — итог для главной сессии

- **Что это:** один скилл «бизнес-аналитик» (MIT, ★0, 4 коммита за один день 2026-07-04, один автор): 16 этапов, 15 западных шаблонов (BRD/SRS по ISO 29148/PRD…), EARS. Только markdown: нет скриптов, сети, хуков. **Безопасность 3.**
- **Гипотеза** «сам задаёт вопросы» — наполовину: режим опроса есть только по явной просьбе, и он слабее нашего `interview-me` (разрешает «небольшую пачку» вопросов, нет догадки, пересказа с Out of scope, явного «да»; по умолчанию выдаёт документ при неполном контексте).
- **Как есть не ставить:** триггер на 143 слова перехватывает 5 наших скиллов (`interview-me`, `session-transcript-analyzer`, `meeting-protocol-builder`, `tr-usecases-acceptance`, `tr-review`) и выдаст BRD/SRS вместо журнала и ТР.
- **Лучшие находки (новое для нас):**
  1. **5 сигналов скрытых требований в рассказе** (актор мимоходом, точка решения, передача, данные упомянуты раз, «и потом как-то…»). Наш `session-transcript-analyzer` берёт только сказанное явно и здесь молчит.
  2. **Правило противоречий:** назвать обе версии, влияние, спросить, записать открытым; не выбирать сторону.
  3. **Уверенность по измерениям** + сигналы «надо хотеть» («наверное хотелось бы», «как у X», общее против частного, «проект меньше, чем звучал»).
- **Вердикт:** адаптировать частично, **10/18**.
- **Куда:** (1)+(2) → шаг 3б в `session-transcript-analyzer`, кандидаты как `Q-N` с `[інтерпретація]`, никогда не `D-N` (предложение в `proposals/odoo19-discovery/`, приоритет высокий); (3) → `boost:interview-me` шаги 1, 3, 4 + `references/should-want.md` (средний); одновременный доступ и «ровно на пороге» → чек-листы `tr-*` (низкий).
- **Не брать:** 16 этапов, IEEE-шаблоны, «один сгруппированный вопрос лучше пяти» (противоречит нашему A/B +1.00).
- **A/B не делали:** 3 кейса описаны в `README.md` → «Проверка», ждут разрешения.
