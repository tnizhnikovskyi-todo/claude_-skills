# ponytail-review

- **Тип:** скилл
- **Источник:** https://github.com/dietrichgebert/ponytail/blob/main/skills/ponytail-review/SKILL.md
- **Версия / коммит:** v5.3.3, `96608e0`
- **Дата разбора:** 2026-11-02
- **Вердикт:** адаптировать (формат вывода и правила проверки, не замена `code-review`)

## Что делает

Ревью изменения (незакоммиченное, ветка, PR, файлы). Читает не только дифф, но
и вызывающих/вызываемых, тесты, README; ищет ожидаемую нагрузку в репо и
явно её называет. Порядок важности: корректно → безопасно → держит нагрузку →
протестировано → быстро → компактно. Каждая находка обязана иметь конкретный
кейс («такой вход даёт такой неверный результат»), иначе не репортится.
Вывод простым языком: «What this change does», затем Must / Should / Nice с
сквозной нумерацией, у каждой находки 4 части: *что это / проблема / фикс /
что будет, если не чинить*. В конце `Verdict`, `Lean: -N lines`, `Not checked`.

## Какую слабость Claude закрывает

Ревью, которое смотрит только дифф и пропускает поломки в нетронутых файлах;
расплывчатые «consider…» без конкретного сценария.

## Сравнение с тем, что есть

Встроенный `code-review` уже ищет баги с уровнями усилия и субагентами
проверки. Новое у ponytail: обязательная оценка нагрузки, блок «lean»
(delete/reuse/stdlib/yagni/merge/split) и 4-частный формат, понятный
нетехническому читателю (полезно для отчётов клиенту и PM).

## Оценка

| Критерий | Балл | Комментарий |
|---|---|---|
| Прирост | 1 | Сильное пересечение с `code-review`; плюс формат и «lean» |
| Частота | 3 | Каждый PR |
| Надёжность | 2 | Явная команда, но качество зависит от модели |
| Стоимость контекста | 3 | ~1.3 тыс. токенов, только при вызове |
| Безопасность | 3 | Только текст, кода не меняет |
| Поддержка | 3 | Активно |
| **Итого** | **15** | |

## Что взять

4-частный шаблон находки и правило «нет конкретного кейса = нет находки»
можно добавить в `pr-review` из `odoo19-mvp-build` или в свой скилл ревью.
