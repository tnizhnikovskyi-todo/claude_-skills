## Что делает

Берёт уже найденные подозрения на уязвимость и для каждого выносит
TRUE POSITIVE / FALSE POSITIVE с доказательствами. Сам баги не ищет.

## Как устроен

1. **Шаг 0: перескажи находку своими словами** (что, корень, триггер,
   влияние, модель атакующего, класс бага). «Половина ложных срабатываний
   разваливается на этом шаге».
2. Маршрут: стандартная проверка (линейный чек-лист) или глубокая (граф
   задач, субагенты) по признакам: межкомпонентный путь, гонки, логика без
   спецификации.
3. **6 ворот** (`references/gate-reviews.md`): процесс, достижимость,
   реальное влияние, PoC, математические границы, защита окружения. Любые
   не прошли — FALSE POSITIVE.
4. **Таблица «рационализаций»**: мысли-ловушки модели («похоже на дыру,
   значит дыра», «явно критично» — «LLM склонны видеть баги и завышать
   severity»).
5. Пакетный режим: шаг 0 для всех, потом проверка, в конце поиск
   **цепочек эксплуатации** из отклонённых по отдельности находок.
6. `false-positive-patterns.md`: 13 типовых ложных срабатываний
   (валидация выше по стеку, внутреннее хранилище ≠ ввод атакующего,
   TOCTOU без доказанной параллельности…). Много про C/память.

## Сравнение с нашим

Наше предложение `security-review` (метод Strix, `proposals/odoo19-mvp-build/security-review/proposed/`)
уже закрывает каждую находку как `confirmed` / `ruled_out` / `open_proof_gap`,
калибрует severity «понижай, не удаляй» и требует контрпримера. Это то же
ядро. **Сверх нашего у fp-check:**

- шаг 0 «перескажи находку точно» до анализа;
- явные ворота «достижимость» и «защита окружения» (для Odoo: `ir.rule`,
  `groups=`, `auth=`, мультикомпания);
- поиск цепочек из отклонённых находок;
- таблица мыслей-ловушек.

**Хуже нашего:** бинарный вердикт без `open_proof_gap` (наш честнее), нет
Odoo-специфики, глубокий режим дорог (субагенты — у нас это в 1.5–5 раз
дороже, `synthesis.md` п. 5).
