## Что изменил автор пакета

`code-review` сильно переписан относительно официального:

- **Граница недоверенных данных:** файлы, дифф, описание PR, правила
  проекта, вывод инструментов — данные; секреты заменять `[REDACTED]`.
- **Замороженный скоуп:** режимы PR / range / local; для PR пин
  `baseRefOid`/`headRefOid`, `merge-base`; манифест скоупа с SHA-256 всех
  файлов; перед каждым шагом пересчитать хеши, при расхождении покрытие
  «неполное».
- **7 ролей детекции** параллельно (2 по правилам проекта, дифф, глубокий
  контекст, конкурентность, ошибки/края, покрытие тестами), затем
  перекрёстная проверка и валидация.
- **Журнал покрытия** по ролям и путям; «пустой, упавший или частичный
  ответ субагента НЕ означает отсутствие находок».

## Сравнение с нашим

- Встроенный `code-review` уже делает поиск багов с уровнями усилий.
  Ставить ещё один `code-review` — конфликт триггеров.
- В `synthesis.md` п. 2 и п. 5: модель и так находит баги по прямой
  просьбе, а субагенты в 1.5–5 раз дороже. 7 ролей + валидация — это
  дорогой вариант, прироста на наших задачах не ожидаем.
- Хеши и манифест — переусложнение для нашего масштаба.
- Описание PR как недоверенный ввод у нас уже есть (`security-review`
  proposed).

**Сверка с действующим `pr-review`** (`@7acde05`): там есть раунд из 4 критиков-субагентов, при недоступности — «single pass». Правила «упавший или частичный ответ критика = не проверено» нет. Идея ложится прямо в этот раздел.
