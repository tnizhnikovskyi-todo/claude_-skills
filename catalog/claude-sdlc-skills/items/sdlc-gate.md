- **Тип:** скилл (+ 2 stdlib-скрипта)
- **Источник:** https://github.com/TsCarpe/claude-sdlc-skills/tree/49ef0b3/skills/sdlc-gate
- **Версия / коммит:** `49ef0b3` (2026-10-28)
- **Дата разбора:** 2026-11-03
- **Вердикт:** адаптировать идеи (перекрёстный вывод, маховик ложных срабатываний, правила раунда); как есть не ставить

## Что делает

Обязательный гейт после технического дизайна и тест-кейсов, до кода.
По уровню риска (A/B/C, ставится при приёме требований) запускает
4 / 2 субагента со свежим контекстом или самопроверку основной сессией.
Роли: 1 архитектура, 2 данные и SQL, 3 тестируемость, 4 **перекрёстный
проверяющий** — единственный, кто читает и design, и cases. Выход —
файл `review/issues-<дата>.md` со статусом «ждёт решения»; человек
по каждой единице решает «внести правку / отклонить с причиной / под
вопросом». Скрипт `check_trace.py` проверяет счётчики и ссылки,
`guard_dev.py` не пускает в разработку без статуса «допущено».

## Чем отличается от нашего отклонённого `independent-check`

| | `independent-check` (у нас, Δ=0) | `sdlc-gate` |
|---|---|---|
| Что проверяют | Один артефакт (код/решение) | Два артефакта, выведенные из одного требования независимо |
| Откуда сигнал | Свежий критик ищет ошибки | Расхождение двух независимых пересказов требования |
| Что ловит сверх модели | Ничего: модель и так находит ошибки по прямой просьбе | Неоднозначность требования: каждый артефакт внутренне согласован, а вместе — «два разных продукта» |
| Условие | — | cases **запрещено** читать design (`sdlc-test` «独立性纪律»), иначе сравнение вырождается в проверку согласованности |
| Кто решает | Судья-субагент | Только человек; класс 3 (разное толкование) — всегда к заказчику/PM |

Роли 1–3 гейта по сути и есть `independent-check` (враждебный промпт —
тот же, что в `sdlc-doubt`, из addyosmani/agent-skills). Их прирост мы
уже измерили: 0. Новое — только роль 4 и обвязка процесса.

## Как устроен (главное)

- **Перекрёстный проверяющий** (`references/cross-check-guide.md`):
  7 измерений (покрытие функций; пути состояния; поля в ассертах;
  границы; права и роли; ошибки и валидации; конкурентность и
  совместимость). Три класса расхождений по приоритету:
  1) в дизайне есть — в тестах нет → дописать тест;
  2) тест утверждает — в дизайне нет → проверить дизайн;
  3) обе стороны есть, но по-разному → **к человеку**, самой не решать.
  «Двойная слепая зона» (обе стороны одинаково пропустили) — НЕ
  расхождение, это задача роли 3; в конце одной строкой.
- **Фильтр RECONCILE:** вывод субагентов — данные, не вердикт; 4 класса
  (не понял контракт / по делу / осознанный компромисс / шум); при
  споре — точечное чтение кода только названного класса, без
  «исследования».
- **Слияние по корню:** человек решает «единицы решения», а не находки.
- **Маховик ложных срабатываний** (`references/false-positive-patterns.md`):
  каждое «отклонить» с причиной → строка в файл; 3–5 последних
  подставляются в промпт следующего ревью; 3 повтора → «[закреплено]».
- **Повторный раунд** (SKILL.md «复审轮规则»): (1) в каждый субагент
  передаются решения прошлого раунда на уровне «заголовок + решение +
  причина», ранее отклонённое без нового основания не поднимается;
  (2) смотрят только изменённые разделы и связанные; (3) если на 3-м
  раунде ещё есть новые высокие — «предохранитель», стоп, вернуть на
  переработку дизайна, а не латать.
- **Подача решения человеку:** сначала в тексте 4 части (сценарий
  простыми словами / что сломается / последствия, если не чинить /
  варианты), потом вопрос; ≤4 вопроса за раз; высокие и все расхождения —
  по одному, средние/низкие — пакетом с предзаполненным решением
  (меньше 15 — всё по одному).
- **Допуск ≠ ack:** подтверждение дизайна в трекере не считается
  допуском; пропуск гейта только по фразе «确认豁免本次 gate» с файлом
  из 7 полей.

## Сравнение с нашим

- `odoo19-mvp-build:pr-review` (по `proposals/odoo19-mvp-build/`):
  смотрит код против SPEC, вердикт APPROVE / REQUEST CHANGES / BLOCK.
  Гейт стоит раньше (дизайн + тесты до кода), у нас аналога на этой
  точке нет: ТР проверяет `tr-review` одним проходом.
- В нашей цепочке ТР нет независимости: `tr-odoo-tech-design` пишется
  после и с опорой на AC из `tr-usecases-acceptance`. Значит, роль 4
  у нас пришлось бы заводить искусственно: «слепой» вывод AC/тестов из
  раздела функциональных требований, не читая AC и тех. дизайн, затем
  сравнение по 7 измерениям.
- `track-convergence` не видел (приватный репо закрыт); правила раунда
  и предохранитель на r3 стоит сверить с ним.
- Маховик ложных срабатываний для `pr-review`/`security-review` у нас
  нет; ближайшее — `skill-feedback` (`observations/`), но он про правки
  скиллов, а не про калибровку ревью.

## Риски

- Цена: A-уровень = 4 субагента + основная сессия; по нашему опыту
  (`synthesis.md` п. 5) — в 1.5–5 раз дороже. Брать только роль 4.
- Описание перехватывает «начать разработку / писать код».
- Прирост роли 4 не измерен ни автором, ни нами — без A/B не включать.
