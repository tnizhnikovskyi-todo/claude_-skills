## Что делает

Цепочка SDLC одного автора для Java + MySQL + Feishu: приём и аудит PRD
(`sdlc-intent`) → дизайн (`sdlc-design`) и тест-кейсы (`sdlc-test cases`),
выводимые **независимо друг от друга** → враждебный гейт (`sdlc-gate`) с
решением человека → разработка → тесты в браузере и Playwright-регресс.
Сбоку: перепроверка решения (`sdlc-doubt`), визуальная сверка с Figma,
чек-лист релиза, хук-линтер, синхронизация со своей веб-платформой.
Всё по-китайски, артефакты — markdown в `sdlc/<требование>/`.

## Какую слабость Claude закрывает

1. Ревью требований видит написанное, но не пропуски — слой 7 и опорные
   таблицы `sdlc-intent`.
2. Один автор пишет дизайн и тесты по одному толкованию требования,
   и ни один ревьюер этого не видит — независимый вывод двух артефактов и
   сравнение их `sdlc-gate` (роль 4).
3. Повторное ревью «по кругу» и ложные находки, которые повторяются, —
   правила раунда и маховик отклонённых.

## Как устроен

- **Права и сеть.** Скрипты stdlib (`re`, `json`, `pathlib`); телеметрии
  нет. Сеть: `verify_dev.py` — `urllib` к health/smoke-URL из конфига
  проекта (localhost); `sdlc-sync` велит Claude делать `curl` к
  `SDLC_PLATFORM_URL` (по умолчанию `127.0.0.1:8080`, кода платформы в
  репо нет); `parse_doc.py` вызывает `lark-cli` для скачивания медиа Feishu.
  `verify_dev.py` исполняет команды сборки и запуска из `sdlc/env/*.md`
  через `shell=True`.
- **Хуки.** В манифесте нет. Шаблон `sdlc-guardrails/templates/settings-hook.json`
  (`PostToolUse` Write|Edit → `check.py`, 20 с) пользователь вливает сам.
- **Что ставится.** `npx skills add` или маркетплейс; для регресса
  `@playwright/test@1.61.0` в `sdlc/`; внешние MCP `codegraph`, `mysql`,
  `chrome-devtools` — свои у пользователя.
- **Триггеры.** `sdlc-gate` срабатывает на «начать разработку / писать
  код» (сам отключается, если нет `sdlc/`); описания по 600–1000 байт.
- **Контекст.** SKILL.md 60–218 строк (CI держит <500), references
  грузятся по шагам; на уровне A гейт = 4 субагента + основная сессия.
- **Качество.** CI проверяет ссылки, синхронность враждебного промпта
  между gate и doubt, счётчики, самотесты парсеров. Eval-сценарии
  (15 у gate, 13 у intent) описаны, **результатов прогонов нет** (числа
  удалены из README коммитом `00c891b`, «删实测数字»).

## Проверка

A/B не делали: чужой код не запускали, адаптированных текстов нет.
Предлагаемый план (нужно разрешение, ~3 кейса × 3 прогона × 2 плеча):

| Кейс (фикстура ТР) | Без (`tr-review` как есть) | С (вставка) |
|---|---|---|
| ТР, где FR «ліміт заявок» неоднозначен, а AC и тех. дизайн согласованно выбрали одно толкование | ожидаем: не видит | «слепой» вывод AC из раздела 1 даёт другое толкование → класс 3, вопрос клиенту |
| ТР с полем `td.*` в форме, которое нигде не используется, и `compute` на параметр без `res.config.settings` | ожидаем: частично | слой 7 ловит оба |
| ТР с редактируемой формой и `readonly` по `state` | AC без «сохранить без изменений» | G1–G4 в AC |
| Контроль: чистый ТР | 0 высоких | 0 высоких (ложные не растут) |

Критерий: прирост находок по ключу > 0 при ложных высоких = 0 и цене
не более 2× (для кейса 1 — честно сравнить со скриптом «просто попроси
сравнить AC с FR», иначе повторим ошибку `independent-check`).

## Риски и заметки

- **Прирост главной идеи (п. 1) не измерен** ни у автора, ни у нас; она
  ровно на границе отклонённого `independent-check`. Отличие в том,
  что сигнал — расхождение двух независимых выводов, а не поиск ошибок
  одним критиком. A/B до включения обязателен, с контрольным плечом
  «просто попросить сравнить AC с требованиями».
- Тексты `pr-review`, `track-convergence`, `testing` не сверены:
  `add_repo` маркетплейса отклонён. `tr-review`, `tr-usecases-acceptance`,
  `odoo-spec-writer` сверены по `~/.claude/skills/synced/`.
