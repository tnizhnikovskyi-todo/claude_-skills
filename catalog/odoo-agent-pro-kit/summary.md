# odoo-agent-pro-kit — итог для главной сессии

- **Что это:** платформа VPCS для разработки модулей Odoo 17–20 агентами: 31 скилл, 5 команд (plan → code → test), хуки на 7 событий, MCP метаданных, Docker-песочница. Apache-2.0, активна (200 коммитов за 3.5 мес.), ★8. Гипотеза подтверждена.
- **Вердикт:** адаптировать выборочно, **9/18**; как плагин не ставить — дублирует `odoo19-mvp-build` и `odoo-connector`, завязан на их окружение, ≈ 2 тыс. токенов описаний всегда, guard блокирует `git push` внутри Odoo-модуля.
- **Лучшая находка:** PostToolUse-линтер версионных ловушек (`checks/odoo_lint.py`): после записи файла модуля регэкспами ловит `<tree>`, `attrs=`, `type='json'`, `<group expand>`, `res.groups.category_id` и возвращает ошибку с исправлением. Это барьер ровно на нашу главную слабость (факты Odoo 19, `synthesis.md` п. 3).
- **Точность:** 7 фактов Odoo 19 подтверждены по исходникам 19.0; ошибки — `jsonrpc` советуется для 18.0 (там нет), `<act_window>` в RNG-разделе, `_sql_constraints` в 19 игнорируется целиком (линтер лишь предупреждает), `OdooTools19` ссылается на несуществующие файлы. Нашу ловушку `res.partner.mobile/title` кит не ловит.
- **Взять:** (1) новый `boost:odoo19-lint` — stdlib-скрипт + опц. хук только warn, правила кита для 19 + наши (`mobile`/`title`, `_sql_constraints`, `res.groups.users`, `ir.cron numbercall`, `view_mode tree`, `self._context`), у каждого цитата из 19.0; нужен A/B. (2) Проверенные факты (группы `privilege_id`, поиск без `expand`, `NewId`+`.get()`, чек-лист `@route`) — в `lean-change/references/odoo19.md`. (3) Владельцам пресейла/ТР — входной контроль ТЗ и проверку имён модулей по манифестам из `OdooRequirementGapAnalysis`.
- **Открыто:** тексты `odoo19-mvp-build:scaffolding`/`code-dev` в контейнере недоступны — сравнение только по назначению; A/B не делали.
