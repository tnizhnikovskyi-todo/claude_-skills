## Что делает

Методичка пресейла (Solution Consultant) в виде плагина, независимого от
вендора: скиллы спрашивают продукт, возможности и конкурентов у
пользователя. Покрывает весь путь сделки: квалификация (MEDDPICC, TFQ),
дискавери (коммерческое и функционально-техническое), карта бизнес-проблем,
демо (Tell-Show-Tell, персона, Picture Pitch, прогон), ценность (ROI,
стресс-тест бизнес-кейса), сделка (PoC, возражения, цена, переговоры,
чемпион, план закрытия), RFX и анкеты безопасности, передача во внедрение
(OSD, архитектура), разбор выигрышей и проигрышей, плюс личный «второй мозг»,
LinkedIn, генераторы PPTX/DOCX/Excalidraw и инструменты руководителя.
Опирается на книгу и явно помечает, что из книги, а что практика кита.

## Какую слабость Claude закрывает

**Метод** (п. 2): дисциплину, которую модель сама держит нестабильно.
Сильнейшие приёмы:

- **«Отсутствие ≠ прохождение».** Каждое утверждение помечается 🟢/🟡/🔴;
  нехватка данных блокирует положительный вердикт, а не округляется вверх.
- **Неусредняемые шлюзы.** Высокий средний балл не выкупает проваленный
  обязательный критерий; есть стоп-лист для мгновенной паузы.
- **Чистая копия для клиента.** Из внутреннего документа с тегами
  собирается клиентский: неподтверждённое убирается или превращается в
  вопрос клиенту.
- **«Потребляй, не извлекай заново».** Одна схема итогов звонка, все
  следующие скиллы читают её, а не сырой транскрипт.

Знаний (п. 1) почти не даёт: справочник по книге закрыт лицензией, а
вендорных знаний нет по замыслу.

## Как устроен

- Корень репозитория = корень плагина. `skills/<имя>/SKILL.md` с
  `version`/`last_updated`, шагами, разделом «Connected Tools» (CRM,
  база знаний, почта; всё опционально), «Handoff» и чек-листом качества.
- Тонкие команды-обёртки в `commands/<фаза>/`; маршрутизатор
  `/presales:guide`.
- `DEAL_TEMPLATE.md`: папка сделки с нумерованными файлами
  (`01_account-brief.md` … `08_competitive-read.md`), запись в неё только
  с подтверждением.
- Скрипты: python-docx/python-pptx/openpyxl через `uv run --with <пин>`;
  рендер Excalidraw через Playwright + unpkg; `.tsx`-артефакты для claude.ai.
- Поддержка качества: CI проверяет JSON манифестов и frontmatter;
  `scripts/desc_budget.py` считает бюджет описаний (лимит 1024 на скилл,
  цель 16 000 символов на всё) и имеет `--self-test`.
- Сеть и права: подробно в `notes.md`. Телеметрии нет.

## Сравнение с нашим набором продаж по стадиям

Сверено по текстам `odoo19-sales-*` из публичного
https://github.com/tnizhnikovskyi-todo/sale_todo_claude (`plugins/`,
коммит `2a7f7c1`). Первая версия таблицы была по описаниям и переоценивала
новизну; исправлено.

| Стадия | Наше (`odoo19-sales-*`) | У них | Сверх нашего | У нас лучше |
|---|---|---|---|---|
| Бриф, журнал | `brief-transcript-analyzer`, журнал D/X/G/Q/C/P/ST/R/A, регистры 1/2/3, «Чего не вигадуємо» | `discovery-sales` (MEDDPICC), `critical-business-issue-finder`, `do-nothing-buster`, `champion-health`, `confidence-tagger` | **проблема ≠ симптом ≠ хотелка, событие-срок; риск «ничего не делать»; сила чемпиона по поведению** — у нас нет; тег уверенности на каждом утверждении брифа (у нас статусы есть у `G-N`, `R-N`, тегов на болях нет) | трассировка ID до `AC-01`, обещания продажника `P-N`, запись в `crm.lead`, клиентский регистр без белых пятен = их «чистая копия» |
| Квалификация, оценка | `data-completeness-scorer` (коэф. ×1,5/×2/×3 от `Q-N [КО]/[ВО]`), `preliminary-estimate` (аналоги из Odoo, таймшиты), стоп-сигналы `ST-N` | `tfq`, `deal-prequal`, `capability-mapper` (fit table) | **явный вердикт «вкладываться в демо / условно / пауза»** с неусредняемыми критериями (у нас решение «демо нужно» принимает человек, `ST-N` фиксируют сигналы, но не дают вердикт); пометка «обязательное» с вето у требования | категории `G-N` стандарт/конфиг/код/интеграция/вне скоупа/неизвестно, правило Studio, «неизвестно» блокируется `[КО]` — сильнее их OOTB/Config/Dev/Gap; оценка трудозатрат, которой у них нет вовсе |
| Демо | `demo-build-plan` (≤ 5 процессов, приоритет по болям `D-N` и обещаниям `P-N`), `demo-base-builder`, `demo-runbook` (хронометраж, «кажемо дослівно», «клієнт має побачити», порядок сокращения), `demo-debrief` | `demo-storyboard`, `demo-dryrun-coach`, `video-demo-creator` | **рассказ от первого лица персоны; пауза и проверочный вопрос после модуля; репетиция-прогон с вердиктом готовности**; открытие серией образов | сценарий по реальному снимку стенда, клики и пути меню, «не імітуємо інтеграцію», разбор расхождений с журналом |
| КП, защита | `offer-finalizer`, `defence-brief` (≤ 7 возражений из `P-N` и истории потерь, межа торгу = нижняя граница, слабые места), `defence-debrief` | `pricing-positioning`, `business-case-stress-tester`, `negotiation-prep`, close-plan | **стресс-тест экономики проекта глазами финансиста** (атаки, чувствительность, консервативный сценарий); позиции «идеал / приемлемо / уходим» по каждой переменной, не только по цене | возражения из реальных потерь по галерее с проверкой применимости; межа торгу как арифметика |
| После сделки | `deal-revival-check`, `loss-pattern-analyzer`, `handover-dossier-builder` | `win-loss-analyzer` | формат группового разбора без поиска виноватых (мелочь) | разморозка сделки, паттерны потерь по базе, досье передачи в дискавери |
| Вне набора | — | second-brain, LinkedIn, PPTX/DOCX, TOC/BBiT, руководитель, RFX, анкеты безопасности | `rfx-navigator` (если часто тендеры; у нас `ST-N` 05 только отмечает тендер) | остальное не нужно |
