## Что делает

Один скилл `odoo-dev` для Odoo 16–19 (и «20+»): определяет версию по манифесту
(по умолчанию 18), каркас модуля генерирует скриптом `scaffold.py`, при
портировании и ревью сначала запускает `check_compat.py` — регэкспы
«устарело в версии N» с выводом `файл:строка`. Плюс короткие шаблоны
(модель, вью, права, крон, отчёт, контроллер), тесты и тайская локализация.

## Какую слабость Claude закрывает

Ту же, что T1/T2: модель пишет конструкции старых версий (`<tree>`, `attrs`,
`name_get`). Барьер — скрипт, а не текст, что верно по нашим принципам.

## Сверка правил с `odoo/odoo@19.0` (`e0b25b7`)

Подробно, с `файл:строка` — в `notes.md`.

| Итог | Число |
|---|---|
| Правил всего | 15 |
| Верны по сути | **15** |
| Ошибочных | **0** |
| Верны, но регэксп уже нужного | 4 (`states`, `<tree>`, `view_mode`, `type == 'product'`) |
| Устаревшая подсказка | 2 (`(verify)` у верных фактов 19; «добавь `@odoo-module`») |
| Уже есть в T2 (`odoo19-lint`) | 10 |
| **Нет в T2** | **5**: `create-single`, `oe_chatter`, `osv-expression`, `assets-xml`, `legacy-js` |
| Есть в T2, нет у panus | 14 |

Ключевая находка — `@api.model` на `create`. В 19.0 это не просто устарело:
`odoo/orm/decorators.py:322-323` молча переделывает метод в
`model_create_multi`, и обёртка (`:364-369`) передаёт ему **список**. Тело под
dict (`vals.get`, `vals['x'] = …`) падает без предупреждения в логе. Модели
пишут так часто (код из 16 и старше) — это правило для T2 уровня ERROR.

По ходу сверки нашли то, чего нет ни у panus, ни в T2: `_constraints = [...]`
в 19.0 игнорируется с warning, как и `_sql_constraints`
(`odoo/orm/model_classes.py:159-161`).

И ещё: в 19.0 есть `odoo/upgrade_code/` — скрипты самого Odoo для
`odoo-bin upgrade_code` (`17.5-01-tree-to-list.py`, `18.1-00-sql-constraint.py`,
`18.1-02-route-jsonrpc.py`, `18.5-00-deprecated-properties.py`…). Официальный
эталон для правил T2 с автозаменой; в отчёте T2 его нет.
