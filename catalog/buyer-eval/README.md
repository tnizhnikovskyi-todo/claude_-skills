## Что делает

ИИ-аналитик покупателя B2B-ПО. По списку вендоров собирает их **заявления**
(сайт, документация, ответы ИИ-агентов вендоров), проверяет каждое
доказательствами, присваивает статус (Verified / Qualified / Contradicted /
Unverified / Unknown), «основание» (на чём держится статус) и уверенность,
прогоняет «вызов» — попытку опровергнуть лидера — и выдаёт Decision Brief
(чат + HTML) для закупочного комитета: «что нашли», таблица «заявление ↔
доказательство», «что ещё выяснить до покупки» (critical / important /
useful), «что может изменить оценку», вопросы на следующее демо с «на что
слушать». Два режима: Quick (по умолчанию, 8–12 поисков на вендора) и Deep
(почему сейчас, жёсткие ограничения, 2–4 вопроса эксперта по категории,
разговоры с агентами вендоров, риски компании, оценка 1–5 по 7 измерениям).

## Чем это полезно нам

Это **взгляд клиента на наш пресейл**. Заказчик внедрения Odoo (или его ИИ-
ассистент с таким скиллом) будет раскладывать то, что мы говорим и пишем, по
той же лестнице: «вендор говорит» → «вендор письменно обязался» → «подтвердил
кто-то независимый» → «есть в нашем КП». Наши `odoo19-sales-*` сильны в
аргументации по фактам проекта (`G-N`, демо, аналог), в межі торгу и в
обещаниях `P-N`. Но с позиции покупателя почти всё это — **заявления
вендора**, а целые измерения закупки у нас не покрыты (см. ниже).

## Данные, сеть, воронка вендора

Подробно: [`items/data-flows.md`](items/data-flows.md). Коротко:

| Что уходит | Куда | Согласие |
|---|---|---|
| Домен каждого оцениваемого вендора (`GET /discover`) | Lambda Salespeak (`hpklbne62y3...lambda-url.us-west-2.on.aws`) | **Нет**, на каждом запуске |
| Вопросы к ИИ-агенту вендора (`POST /chat`) | Та же Lambda → агент вендора-клиента Salespeak, «агенты вендоров логируют разговоры» | **Нет** |
| Версия (`VERSION`) | GitHub raw, раз в 6 ч | Нет |
| `git pull --ff-only origin main` | GitHub | Да, вопрос перед обновлением |
| Телеметрия: домены вендоров, категория, **тексты вопросов к вендорам и вопросов эксперта покупателю**, счётчики, баллы, лидер | AWS API Gateway Salespeak | Opt-in, вопрос один раз после брифа |
| Профиль покупателя (компания, размер, стек, жёсткие ограничения **вкл. потолок бюджета**) | Локально `~/.salespeak/` | Пишется после запуска |

**Это маркетинговая воронка, но прозрачная.** Salespeak продаёт вендорам
ИИ-агентов для сайта; скилл даёт покупателям повод с этими агентами
говорить и собирает спрос: `MEASUREMENT.md` прямо называет `discover`
«лучшим счётчиком запусков, не зависящим от согласия» и предлагает
группировать логи Lambda по **IP источника**. История хуже текущей
версии: в v3 агент вендора был «авторитетным источником», а «полнота
доказательств» поднимала вендоров с агентом Salespeak; в v4.0.0 это
убрано и записано правило нейтральности. В v3.5 объём телеметрии
расширили для уже согласившихся без повторного согласия.

Для нас вывод двойной: (1) сам скилл не ставим; (2) если наш клиент
пользуется таким инструментом, всё, что мы говорим через сайт и чат-бота,
пойдёт в его бриф как «заявление вендора», а не как доказательство.

## Оценка

| Критерий | Балл (0–3) | Комментарий |
|---|---|---|
| Прирост | 1 | Как инструмент — для покупателя, не для нас. Ценность в 5–6 вставках «глазами клиента» |
| Частота | 1 | Сам скилл нам почти не нужен; вставки сработают в каждой сделке |
| Надёжность | 2 | Чёткие правила, рендерер принуждает «Verified ≠ только заявление», история правок по тестам (CHANGELOG). Нашего прогона нет |
| Стоимость контекста | 1 | 10–14 тыс. токенов на вызов; грузится только по вызову |
| Безопасность | 1 | Код прочитан, stdlib, без хуков и MCP. Но без согласия шлёт домены вендоров и вопросы в Lambda Salespeak (с планом анализа по IP), `curl` проверки версии на каждом запуске, пишет в `~/.salespeak/` |
| Поддержка | 2 | Компания-автор, активен (v4.1.1 от 2026-09-28), ★69, но один коммиттер |

## Риски и заметки

- **Не ставить** и не запускать даже для пробы: первый же запуск отправляет
  домены вендоров в Salespeak.
- Банк вопросов — под SaaS (ARR, seats, SOC 2). Для Odoo-интегратора в
  Украине переписан своими словами в `items/buyer-diligence-questions.md`;
  без проверки на реальных сделках это гипотеза (у нас правило
  `demo-runbook`: «не пишемо типові питання з голови»). Перед вставкой
  сверить с `loss-pattern-analyzer` и записями `defence-debrief`.
- Вставки 1–2 нужно мерить A/B на `defence-brief` (с/без колонки «як це
  побачить клієнт» и списка измерений): прирост не измерен.
- Наблюдение для маркетинга, не для скиллов: клиентские ИИ-ассистенты
  засчитывают маркетинговые страницы как «заявления», а документацию,
  страницы с ценами и условиями — как «документ вендора». Публичные
  условия поддержки/SLA и кейсы с контактом референса повышают наш
  «статус» в таких брифах.
