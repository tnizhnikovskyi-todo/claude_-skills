- **Источник:** `salespeak-ai/buyer-eval-skill@ebb0e06`, `references/evidence-model.md`
  (15 КБ), плюс `bin/render_report.py` (принуждение правила), MIT
- **Вердикт:** адаптировать (пересказ) → `defence-brief`, `offer-finalizer`,
  `boost:source-check`

## Суть

Каждый вывод о вендоре строится из **заявлений** (конкретных, проверяемых;
лозунги не в счёт) и доказательств к ним.

**Типы источников** по тому, кто их контролирует:

| Тип | Пример | Что может подтвердить |
|---|---|---|
| Заявление вендора | сайт, маркетинг, кейсы вендора, ответы ИИ-агента/чат-бота | ничего само по себе |
| Документ вендора | справка, API, страница безопасности, публичный прайс, опубликованные условия договора | только узкие самоописательные факты («API есть», «сертификат заявлен») |
| Независимое | отзывы на самой площадке, рассказы клиентов, аналитики, пресса, реестры | возможности и **исходы** |
| Контент конкурента | «X vs Y», «альтернативы X» | ничего; только как наводка |
| Документ покупателя | КП, ответы на RFP, заметки демо | то, что предложили **этому** покупателю |

**Статусы:** Verified / Qualified (верно, но с существенной оговоркой:
тариф, доплата, усилия) / Contradicted / Unverified (не нашли
подтверждения — не значит ложь) / Unknown (часть, которая важна, нигде не
оценивается).

**Основание** (что решило статус) показывается рядом со статусом, чтобы
«подтверждено документацией вендора» не выглядело как «подтверждено
независимо». Рендерер не показывает Verified на основании «только
заявление».

Правила, важные для нас:
- **Заявления об исходе** (срок внедрения, ROI, «легко», удовлетворённость)
  документ вендора не подтверждает — только независимое или документ
  покупателя.
- Когда собственные источники вендора расходятся (маркетинг/бот vs
  документация/прайс) — **Contradicted**.
- «Нет доплат», «нет поручительства» — Verified только по тексту договора/
  прайса, не по FAQ.
- Два источника, повторяющие один первоисточник, — один источник.
- Читать страницу, а не сниппет; **у WebFetch просить цитату по теме, а не
  подтверждение факта** (в тестах сводка вернула вопрос как утверждение
  вендора).
- **Проход-вызов** перед выводом: что сделает лидера неправильным выбором
  (поиск «switching from X», «X alternatives because», жалобы при продлении);
  скрытые условия (тарифы, доп. модули, услуги, миграция, хостинг); один ли
  стандарт ко всем.

## Как это переносится к нам

Мы — вендор. Для клиента (или его ассистента):

| Наше | Как он это классифицирует |
|---|---|
| Слова сейла на брифе и демо, `про-todo.md`, сайт, чат-бот | заявление вендора |
| `G-N`, вилка, аналог из нашей базы | заявление вендора (аналога он не видит) |
| Показанное на демо на стенде | ближе к документу покупателя (он видел сам), но только для показанного сценария |
| КП, ТР, договор, SLA, публичная документация Odoo SA | документ с обязательством |
| Контакт референс-клиента, отзывы, статус партнёра на odoo.com | независимое |

Отсюда вставки:

1. **`defence-brief`, Крок 1:** к полю «Чим підперта» добавить «Як це
   побачить клієнт: наше слово / показали на демо / є в КП чи договорі /
   може перевірити сам (референс, документація Odoo)». Pre-save: ответ на
   заперечення о **сроках, «легкости», окупаемости** не держится только на
   «нашем слове» — нужен референс, документ или показ.
2. **`offer-finalizer`, Крок 6:** всё, что сейл обещал устно про цену и
   «без доплат» (`P-N`), есть в КП текстом; иначе клиент засчитает это как
   заявление и может поймать на расхождении (Contradicted).
3. **`defence-brief`, Крок 3:** короткий блок «Що клієнт знайде сам»
   (публичный негатив + скрытые условия) — см. `buyer-diligence-questions.md`.
4. **`boost:source-check`:** правило нейтрального запроса к WebFetch.

Формулировки — свои, по-украински, в стиле `skill_conventions.md`.
