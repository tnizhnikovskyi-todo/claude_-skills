# generate-test-book: разбор по существу и сравнение с нашими

Источник: `Androbito/generate-test-book@1aa864c`. Лицензии нет: ниже всё
пересказ своими словами, без цитат.

## Формат тест-книги

Один markdown-файл `output/test-book-<key>.md`:

1. Шапка со статусом «сгенерировано, ждёт ревью QA» и (если запускали из папки
   с кодом приложения) предупреждением «область не изолирована».
2. Таблица паспорта: история, ссылка, статус, источники, число AC и сколько из
   них неоднозначны «на момент чтения», число макетов, дата, версия шаблона.
3. AC дословно, на языке истории, без перевода; неоднозначные помечены с
   причиной в одну строку.
4. Что показали макеты — наблюдения привязаны к конкретному AC и подписи макета;
   отдельно AC без макета и нечитаемые макеты.
5. Открытые вопросы к владельцу продукта — закрытые, отвечаемые одной строкой, с
   указанием, на какие сценарии влияют.
6. Область (что покрыто / что нет) и предусловия (окружение, учётка, наборы
   данных TD-xx, платформы).
7. Сценарии Gherkin: на каждый — тег природы (`@nominal` / `@error` /
   `@limit`), тег источника `@ac-N` и строка-комментарий «источник: AC-N,
   уточнено макетом …».
8. Трассировка: сценарий | тип | AC | макет; строка покрытия «n/n AC» и для
   каждого непокрытого AC — «упущение» или «не проверяется вручную».
9. Блок замеров (число AC, сценариев по типам, покрытие, вопросы,
   длительность).

Есть **табличный вариант** для исполнения в таблице: Given → предусловия, каждый
When → строка «Действие», Then → «Ожидаемый результат», плюс пустые колонки
«Фактический результат» и «Статус». Конвертация механическая, без переписывания.

## Покрытие

| Аспект | Что есть | Оценка |
|---|---|---|
| Негативные сценарии | `@error` на каждое условие отказа, названное в AC; `@limit`: пусто, длинный список, нет значения, нет прав, офлайн | Хорошо, но только то, что есть в AC: сам не добавляет «нещасливі» пути |
| Тестовые данные | Отдельный файл: запрет реальных данных (почта только `@example.com`, без карт, IBAN, реальных фото документов), учётки-плейсхолдеры, наборы TD-01…08, граничные значения | Сильная сторона; содержимое под чеки и продукты, нам не подходит |
| Роли | Только плейсхолдеры учёток: основная, вторая, пустая, админ | Слабо: нет матрицы ролей и обязательных проверок прав |
| Платформы | Одна книга, полный прогон на каждой платформе; отдельный сценарий только при реальной разнице макетов | Для нас не нужно (Odoo — веб) |
| Трассировка | Каждый сценарий → AC, покрытие считается, непокрытое объясняется | Главная ценность |

## Механизмы, которых у нас нет

1. **Без AC нет тест-книги.** Если AC нет, скилл останавливается и не выводит
   их из названия, описания или макетов.
2. **Сценарий существует только из AC.** Деталь макета без AC — вопрос
   владельцу продукта, а не тест-кейс. Противоречие макета и AC — тоже вопрос,
   скилл не решает его сам.
3. **Признаки неоднозначного AC** перечислены явно: неколичественный порог,
   условное поведение, «и т. п.», ссылка на нерешённое, противоречие другому
   AC. Такой AC помечается, допущение пишется прямо в шаге сценария.
4. **Счётчик неоднозначности «как пришло»** — не обнуляется после ответов;
   меряет качество истории на входе.
5. **Закрытые источники.** Не читать код, тесты и коммиты тестируемого
   приложения: тест, выведенный из реализации, проверяет код сам собой.
   Запуск из папки с кодом — пометка в документе.
6. **Блокирующий шаг ревью** перед генерацией: план сценариев таблицей
   «название | тип | AC» и вопросы; без явного «да» файл не пишется.
7. **Подписи интерфейса не цитировать**, если язык макета отличается от
   продакшена: описывать элемент по роли и положению, сообщения об ошибке —
   по смыслу. Цитировать только то, что подтверждено на языке продакшена;
   данные, вводимые тестировщиком, цитировать всегда.
8. **Правила шага:** Given — состояние, не действие; один When — одно
   действие; один Then — одно наблюдение; 3–8 шагов; сценарии независимы;
   заголовок — ожидаемый результат, а не действие; без технических деталей и
   оценок вроде «работает корректно».
9. **Не раздувать:** варианты одного поведения — `Scenario Outline` с
   примерами, а не копии.
10. **AC сохраняют исходную нумерацию**, если она есть.

## Сравнение с нашими

### `odoo19-tr-authoring:tr-usecases-acceptance` (текст прочитан)

Наш скилл **пишет** UC и AC в ТР; чужой **исполняет** уже написанные AC в
тест-книгу. Это соседние звенья цепочки, не дубль.

| | Наш `tr-usecases-acceptance` | `generate-test-book` |
|---|---|---|
| Назначение | Автор AC в ТР | Тест-книга из готовых AC |
| «Нещасливі» пути | **Обязательны**: нет данных, ошибка, права, ограничения | Только те, что есть в AC |
| Права/роли | Обязательный AC на видимость для не-админа | Плейсхолдер админа, и всё |
| Неоднозначность | «Не пиши розпливчасті AC» общим правилом | Явный список признаков + допущение в шаге + вопрос |
| Трассировка | «Каждая вимога має AC» (чек-лист) | Каждый сценарий → AC, покрытие n/n |
| Исполнение | Нет | Табличный вариант с колонками факта и статуса |
| Тестовые данные | Нет правил | Отдельный файл, запрет реальных данных |
| Подписи UI | Не оговорено | Описывать по роли, не цитировать |
| Язык | UA, AC EN или UA по проекту | Документ EN, AC дословно |

**Что у них сверх нашего:** признаки неоднозначного AC, трассировка с
подсчётом покрытия, исполнимый табличный формат, правила тестовых данных,
правило подписей UI, «закрытые источники».
**Что хуже:** не добавляет негативных путей и проверок прав сам, роли слабые,
домен — мобильное приложение, вход только из Linear.

### `odoo19-implementation:acceptance-act-builder` (текста нет в контейнере)

По `proposals/siblings-checked.md`: строит акт приёмки из AC в SPEC/ТР и
реестра. Акт фиксирует «принято / не принято»; тест-книга — то, **по чему**
клиент проверяет до акта. Логичная цепочка: ТР (AC) → тест-книга UAT →
прогон у клиента (факт/статус) → акт приёмки ссылается на результаты
прогона. Проверить по тексту скилла, нет ли там уже чек-листа проверки.

## Полезно ли для UAT у клиента

Да, как **идея формата и правил**, а не как готовый скилл. Табличный вариант
(предусловия | шаг | действие | ожидаемое | факт | статус + колонка AC) — по сути
готовый протокол UAT, который клиент заполняет сам. Правило подписей UI прямо
бьёт в нашу боль: макеты и ТР часто на одном языке, а интерфейс Odoo у клиента
на украинском или в другой локализации. Gherkin клиенту не нужен; ему нужна
таблица на украинском.
