# generate-test-book — сводка

**Что это.** Один скилл Claude Code (POC, ★0, 7 коммитов за 2 дня в авг. 2026, **без лицензии**): по ключу истории в Linear читает её AC и макеты, после явного одобрения пишет черновик ручной тест-книги в Gherkin с трассировкой «сценарий → AC». Только markdown, без скриптов и хуков, read-only на бэклоге. Гипотеза подтвердилась; уточнение: AC он не пишет, без них останавливается.

**Лучшие находки:**
- табличный вариант для исполнения (предусловия / шаг / действие / ожидаемое / AC / **факт** / **статус**) — готовая форма UAT-протокола для клиента;
- кейс только из AC; деталь без AC → вопрос; без AC — стоп;
- явные признаки неоднозначного AC + допущение прямо в шаге;
- не цитировать подписи UI из макета, если язык не подтверждён (наша боль с локализацией Odoo);
- покрытие «n/n AC» с причиной для каждого непокрытого; «закрытые источники» (тесты не выводятся из кода).

**Хуже нашего:** не добавляет негативных путей и прав сам (наш `tr-usecases-acceptance` их требует), роли слабые, домен — мобильное приложение, вход только Linear.

**Оценка:** 11/18 (прирост 2, частота 2, надёжность 1, контекст 2, безопасность 3, поддержка 1). **Вердикт: адаптировать** — только идеи своими словами.

Признаки неоднозначности AC добавить в чек-лист `tr-usecases-acceptance` / `tr-review`. Текст `acceptance-act-builder` в сессии недоступен — сверить перед реализацией.
