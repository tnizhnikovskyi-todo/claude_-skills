# Режим `--vendor`: аудит стороннего инструмента перед внедрением

- **Тип:** режим скилла
- **Источник:** `SKILL.md@d5128b0` (раздел Vendor Mode),
  `references/phase6-report.md@d5128b0` (Vendor Report Structure)
- **Лицензия:** нет → только идеи своими словами
- **Вердикт:** адаптировать (формат вердикта и раздела условий)

## Что делает

Режим отвечает на вопрос «безопасно ли нам это внедрить», а не «что
исправить автору». Он пропускает поиск секретов и CVE (это забота
вендора), не запускает чужой код (никакого Docker и PoC) и выдаёт отчёт
для команды безопасности. Отчёт начинается с вердикта.

## Устройство вердикта (пересказ)

- Три вердикта: внедрять / внедрять с условиями / не внедрять. Плюс общий
  уровень риска, его задаёт худшая **подтверждённая** находка с учётом
  достижимости.
- «Не внедрять» ставится, если есть достижимая high/critical находка,
  которую мы не закроем своими силами без правки кода вендора. Или если
  есть любой признак злого умысла: обфускация, эксфильтрация, враждебный
  install-скрипт. Решающая находка называется явно.
- «С условиями»: список условий обязателен, и **каждое условие привязано к
  конкретной находке**. Условия — это меры на нашей стороне: изоляция
  сети, не давать секреты, пин на проверенный коммит, повторный разбор при
  обновлении.
- У каждой находки есть поле «чем можем закрыть сами», либо пометка «только
  правкой вендора».
- В отчёте обязательны разделы «ложные срабатывания» (это повышает
  доверие) и «границы проверки»: что не читали, какие проверки пропущены.
  «Пропущено» не означает «проблем нет».

## Чем полезно нам

Наши вердикты «взять / адаптировать / отклонить» ничего не говорят о
**безопасных условиях использования**. Карточки context7, firecrawl,
graphify уже пишут такие условия в свободной форме: «без клиентских
данных», «только по явному вызову», «пин версии». Если сделать это
обязательным разделом с привязкой к находкам, условия станут проверяемыми
для главной сессии и задач из `roadmap.md`.
