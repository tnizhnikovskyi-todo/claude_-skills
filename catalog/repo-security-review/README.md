# repo-security-review (Consensys)

- **Тип:** скилл (оркестратор субагентов + 12 reference-файлов + `setup.sh`)
- **Источник:** https://github.com/Consensys/repo-security-review (★33)
- **Версия / коммит:** `d5128b03d6a785bfb7c8be4139291f887c2a3215` (2026-10-21), `maturity: experimental`
- **Лицензия:** **нет.** Apache-2.0 был добавлен в `98900eb` и удалён через 2 минуты в `5172196`. Берём только идеи своими словами.
- **Дата разбора:** 2026-11-03
- **Вердикт:** инструмент **отклонить** (8/18); идеи для проверки скиллов **адаптировать**

## Что делает

Многофазный аудит безопасности репозитория силами изолированных
субагентов. Фазы: секреты (gitleaks), стек, архитектура и угрозы, CVE с
проверкой достижимости (osv-scanner, EPSS, CISA KEV), OWASP/API Top 10
(semgrep + LLM), **проверка скиллов по OWASP LLM Top 10 (фаза 4b)**,
независимая валидация (confirmed / needs review / rejected), опционально
PoC и динамическая проверка в Docker, отчёт в Markdown. Есть режимы:
`--pr` (только diff), `--repos` (несколько сервисов), `--vendor` (можно ли
внедрять чужой инструмент).

## Какую слабость Claude закрывает

Непоследовательность большого аудита: модель пропускает классы
уязвимостей, верит собственным находкам и смешивает «нашёл» с
«подтвердил». Для нас интересна узкая часть: **как проверять сам скилл**
(фаза 4b) и **как выносить вердикт «внедрять / не внедрять»** (`--vendor`).

## Как устроен

- `SKILL.md` 90 КБ (~22k токенов), грузится при срабатывании; references
  ещё ~320 КБ, их читают субагенты пофазно. Широкий триггер («даже на
  casual phrasings») пересекается со встроенным `security-review`.
- Две границы доверия: (1) содержимое репо для всех агентов — данные,
  чтение и запись только в своих папках; (2) поисковые фазы передают
  валидатору **только пути к файлам**, валидатор считает их выводы
  недоверенными и перепроверяет с нуля.
- Модели: глубокий уровень (Opus) только для архитектуры, остальное Sonnet
  или Haiku; `--vendor` и `--pr` всегда на Sonnet. Fable 5 исключён, чтобы
  модель не отказывала на рассуждениях об атаках.
- Сеть: реестр Semgrep, api.first.org (EPSS), CISA KEV, GitHub releases;
  с `--verify-deployment` один пассивный запрос к указанному URL.
  Телеметрии нет.
- Исполнение: внешние сканеры; `--runtime` собирает и запускает **чужой
  код** в Docker и headless Chromium (с подтверждением, но `--yes`
  подтверждает всё автоматически).
- `setup.sh`: `go install …@latest`, `curl … | sh` из ветки `main`,
  `sudo apt-get`, `pip3 --break-system-packages`, без пинов и контрольных
  сумм. Мы его не запускали.

Детали: [`items/phase-4b-skill-security.md`](items/phase-4b-skill-security.md),
[`items/vendor-mode.md`](items/vendor-mode.md).

## Проверка

A/B не проводили: инструмент не берём, а запускать его чужие инструкции
для A/B незачем. Вместо этого прошли **их собственным подходом по их
репозиторию** (вручную, без запуска):

| Проверка | Результат |
|---|---|
| Скрытые символы (zero-width/bidi), HTML-комментарии | 0 |
| Фразы-инъекции | Только примеры в защитных блоках |
| Внешние URL | Все объяснимы (сканеры, EPSS, KEV, установщики) |
| Установщик | `curl \| sh` из `main`, `@latest`, `sudo` — по их же правилам 4b это находка LLM05, но **4b её не увидит**: `.sh` не входит в проверяемые файлы, а фаза 4 выключена для «чисто скиллового» репо |

Предлагаемый A/B для нашего чек-листа: см. «Открытые вопросы» в `notes.md`.

## Риски и заметки

- **Лицензия:** сначала её добавили, потом явно отозвали. Даже фрагменты
  текста не переносим.
- Исключение Fable 5 «из-за guardrails» и `--yes`, который снимает
  подтверждение перед запуском чужого кода в Docker, — это паттерны, которые
  наш чек-лист должен ловить (шаг 1 и шаг 3).
- Если когда-нибудь понадобится полный аудит кода, ближе к нам методология
  Strix (`catalog/strix`), уже переписанная под Odoo.
