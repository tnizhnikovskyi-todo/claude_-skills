# Сквозное: соглашения и eval-кейсы

- **Источник:** https://github.com/uycung/ba-skills/tree/214f852 (`evals/`, блок «Conventions», `scripts/validate.py`)
- **Вердикт:** адаптировать идеи для `plugins/boost/evals/` и проверок наших плагинов

## Соглашения (одинаковый блок во всех 11 скиллах)

- Метки происхождения: `[Stated]` (назвать источник), `[Inferred]`,
  `[Assumption]`; ставить только там, где читателю важно различие.
- ID проекта главнее дефолтных; ID не меняется и не переиспользуется;
  свой ID помечается «proposed»; не создавать ID тому, чего пользователь
  не давал. Это совпадает с нашим правилом «AC-01 IDs verbatim» в
  `odoo-spec-writer` и с реестрами D/X/C/T/Q/A.
- `validate.py` проверяет, что блок идентичен во всех скиллах — **барьер
  вместо формулировки** (наш принцип из `criteria.md`). Для наших
  `odoo19-*` можно так же линтом держать одинаковыми общие блоки
  (формат реестров журнала).

## Eval-кейсы

На скилл три вида: **main**, **vague** (неполный вход), **trap** (вход
толкает нарушить собственное жёсткое правило: «придумай имена»,
«заполни все ячейки», «поставь ставку сам»), плюс **standalone** (скилл
без соседей не ссылается на несуществующие файлы). Проверки
структурные: засеянные дефекты должны найтись отдельной строкой с кодом,
«контрольные» хорошие пункты не должны помечаться Blocker, коды и числа —
только из входа, отчёт с Blocker не может быть Ready.

**Что взять:** вид кейса **trap** для наших evals (у `interview-me`
ловушка «как считаете нужным» уже есть — расширить на дискавери:
«запиши как решение то, что клиент сказал «як вважаєте»»). И проверку
«засеянный дефект + контрольный хороший пункт» для `tr-review`.
