# erpipe-org/mcp-odoo (`odoo-mcp`)

- **Тип:** MCP-сервер (Python, stdio / Streamable HTTP) + 4 скилла-плейбука
- **Источник:** https://github.com/erpipe-org/mcp-odoo (★427, MIT; бывш. `tuanle96/mcp-odoo`)
- **Версия / коммит:** 1.3.2, `76ec136` (2026-08-25)
- **Дата разбора:** 2026-11-03
- **Вердикт:** **адаптировать** (идеи в наш `odoo-mcp`; сервер как есть не ставить)

## Что делает

Самостоятельно хостимый MCP-сервер для Odoo 16–19: 41 инструмент (чтение,
агрегация, диагностика прав и вызовов, миграционные отчёты, скан аддонов,
локальный BM25-поиск, бухгалтерские отчёты, кросс-инстанс выборки) и
«шлюзованная» запись `preview_write → validate_write → execute_approved_write`.
Несколько баз — именованные инстансы в одном JSON-конфиге, параметр
`instance` на каждом инструменте. XML-RPC для 16–18, JSON-2 для 19+.

## Какую слабость Claude закрывает

Действия в Odoo без ручных скриптов и с ограждением от опасной записи. Для
нас это пересекается с тем, что уже даёт наш `odoo-mcp`; новое — в
механике безопасности записи и диагностике.

## Как устроен (главное для безопасности)

| Механизм | Как сделано | Сила |
|---|---|---|
| Глобальный выключатель | `ODOO_MCP_ENABLE_WRITES=0` по умолчанию — запись невозможна | сильный, реальный |
| Прямые `create/write/unlink` | запрещены в `execute_method`, только через трёхшаговый гейт | сильный |
| Токен одобрения | `sha256(canonical payload)` с моделью, ids, значениями, контекстом, **инстансом**; хранится в памяти процесса после `validate_write`, TTL 10 мин, одноразовый | защищает от подмены payload/базы, **не от самого агента** |
| Валидация | живой `fields_get`; без доверенных метаданных одобрение не выдаётся | полезно |
| Человек в контуре | только при `ODOO_MCP_ELICIT_WRITES=1` и клиенте с MCP elicitation; иначе тихий фолбэк на токен + `confirm=true`, который ставит агент | **опционально** |
| Методы с побочными эффектами | классификация по имени (`action_*`, `button_*`, `*send*`, `*post*`, `*validate*`), всё неизвестное и побочное — блок, пока точный `model.method` не в allowlist (`odoo_mcp_policy.json` в git с `reviewed_by/date/reason`, fail-closed) | сильная идея |
| Массовые изменения | пакетный `create` ≤ 100; **`write`/`unlink` без предела на число ids** | пробел |
| Невалидный домен | ошибка, а не «все записи» (фикс 2026-08-14) | важная мелочь |
| Аудит | JSONL по событиям preview/validate/execute/chatter, токен как хеш; **`execute_method` не журналируется**; fail-open | частично |
| Field ACL | deny/allow полей по модели/инстансу на всех read-путях | полезно |
| Ключи | пароль/API-ключ бота в конфиге/env, без fallback между инстансами; не per-user | средне |
| Сеть | только Odoo + опциональный OAuth introspection; телеметрии нет; HTTP по умолчанию только localhost | хорошо |

Подробно: [`items/write-gate.md`](items/write-gate.md); скиллы:
[`items/skills-pack.md`](items/skills-pack.md); журнал: [`notes.md`](notes.md).

## Сравнение с нашими коннекторами

| | наш `odoo-mcp` | `odoo-connector` | erpipe `odoo-mcp` |
|---|---|---|---|
| Несколько баз | `connection_id` на каждом вызове, ответ возвращает `connection`, базы через админ-страницу | per-user ключ (по описанию) | именованные инстансы в файле, `instance` необязателен (дефолт молча) |
| Подтверждение удаления | `user_confirmed=true` после «да» в чате (ставит модель) | не проверено | elicitation (если включено) или токен |
| `create`/обычный `write` | без гейта | не проверено | выключены по умолчанию, трёхшаговый гейт |
| Произвольные методы | любой, деструктивные (unlink/*delete*/archive…) требуют `user_confirmed` | не проверено | allowlist точных `model.method`, остальное блок |
| Лимит массовых изменений | неизвестно | неизвестно | только create ≤100 |
| Аудит | неизвестно | неизвестно | JSONL (без `execute_method`) |
| Диагностика прав/вызовов | нет | нет | `diagnose_access`, `diagnose_odoo_call` |
| Правило «уточни перед действием» | есть, в инструкциях сервера | — | нет (только prompt `safe_write_review`) |

Сильнее у нас: обязательный выбор базы и эхо `connection` в ответе (у
erpipe пропуск `instance` молча ведёт в дефолтную базу), правило «грилла»
перед действием, per-user доступ. Сильнее у них: запись выключена по
умолчанию, allowlist методов в git с ревью, привязка одобрения к точному
payload и базе, аудит, человек через elicitation.

## Что перенести в наш коннектор

1. **Allowlist методов в git** для `odoo_execute`: точный `model.method` с
   `reviewed_by/date/reason`, неизвестные методы блок по умолчанию (а не
   только «деструктивные по имени»).
2. **Предел на число записей** в `write`/`unlink`/методах (например 50) +
   обязательный показ списка с `display_name` перед изменением.
3. **Preview с diff «было → стало»**: перед `odoo_write` читать текущие
   значения полей и показывать пользователю (у erpipe этого нет — можем
   сделать лучше).
4. **Невалидный домен → ошибка**, не пустой домен. Проверить наш сервер.
5. **Аудит-журнал** каждого изменяющего вызова (включая методы): кто, база,
   модель, ids, значения, итог.
6. **Подтверждение человеком на стороне сервера** (MCP elicitation), если
   клиент поддерживает — вместо `user_confirmed`, который выставляет сама
   модель. Привязать подтверждение к хешу точного payload + `connection_id`.
7. **None-marshal**: при `cannot marshal None` отвечать «выполнено», чтобы
   модель не повторяла действие.

## Риски и заметки

- Основной вывод: в режиме по умолчанию «подтверждение» — ритуал для
  агента (токен считает сам сервер и отдаёт агенту). Нельзя описывать это
  как human-in-the-loop без `ODOO_MCP_ELICIT_WRITES=1`.
- Cross-instance чтение по всем базам включено по умолчанию (opt-out) —
  для клиентских баз нежелательно.
- README — во многом маркетинг хостинга ERPipe; в коде серверa связи с
  ERPipe нет.
- `odoo-connector` в этой сессии не найден на диске — его сравнение не
  проверено.
