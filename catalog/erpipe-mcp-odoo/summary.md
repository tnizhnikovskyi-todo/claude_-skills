# erpipe-org/mcp-odoo — итог для главной сессии

- **Что это:** self-hosted Python MCP для Odoo 16–19 (MIT, ★427, активен,
  v1.3.2 от 2026-08), 41 инструмент, несколько баз через `instance`,
  XML-RPC/JSON-2, рядом коммерческий хостинг ERPipe. Телеметрии нет.
- **Гипотеза «запись через подтверждение» верна лишь частично:** по
  умолчанию запись **выключена** env-флагом; при включении «подтверждение»
  — хеш-токен preview→validate→execute, который агент проводит сам.
  Человек в контуре только с `ODOO_MCP_ELICIT_WRITES=1` и клиентом с MCP
  elicitation.
- **`odoo-connector` (сверен по коду приватного маркетплейса):** одна база,
  личный API-ключ, 5 инструментов без серверных проверок — `unlink` и
  любой метод проходят; защита только текстом в SKILL.md. Здесь erpipe
  заметно сильнее, и идеи ниже нужнее всего именно ему.
- **Пробелы erpipe:** нет предела ids для `write`/`unlink`; `execute_method` не
  попадает в аудит; preview без «было → стало»; пропуск `instance` молча
  ведёт в дефолтную базу (у нашего `odoo-mcp` это лучше).
- **Лучшие идеи для нашего коннектора:** (1) allowlist точных
  `model.method` в git с ревью, неизвестное — блок; (2) лимит числа
  записей; (3) diff «было → стало» перед записью; (4) невалидный домен →
  ошибка; (5) JSONL-аудит всех изменяющих вызовов; (6) подтверждение
  человеком через elicitation, привязанное к хешу payload + базе;
  (7) `cannot marshal None` = «выполнено, не повторяй».
- **Вердикт: адаптировать** (10/18). Сервер не ставить — дублирует наш
  `odoo-mcp`; переносим механику безопасности записи.
- **Не проверено:** практический прогон (нужно разрешение), код нашего
  `odoo-mcp` (видны только описания инструментов).
