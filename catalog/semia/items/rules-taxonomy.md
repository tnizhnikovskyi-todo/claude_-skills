# Semia: словарь фактов и 11 классов угроз (`semia-core/rules/sdl/*.dl`)

- **Источник:** `packages/semia-core/src/semia_core/rules/sdl/skill_dl_static_analysis.dl@379bc25`,
  `skill_description_lang.dl@379bc25`, словари в `schema.py@379bc25`,
  промпт синтеза в `pipeline.py@379bc25` (`_render_synthesis_prompt`)
- **Лицензия:** Apache-2.0 (проверено по `LICENSE`, заголовки SPDX в файлах)
- **Вердикт:** **адаптировать** как вопросы ручного чек-листа (идея, пересказ своими словами)

## Как устроено

LLM читает скилл и пишет **факты** о поведении: действия (`action`),
вызовы внутри них (`call`), значения (`value`) и связи вход → выход.
Детерминированный Datalog-движок выводит из фактов находки. Правила
сами ничего в тексте не ищут: всё, что LLM не записала, правила не
увидят.

Словари (закрытые, валидатор отклоняет другие значения):

| Что | Значения |
|---|---|
| Эффект вызова | `fs_read`, `fs_write`, `fs_list`, `net_read`, `net_write`, `proc_exec`, `code_eval`, `env_read`, `env_write`, `db_read`, `db_write`, `chain_write`, `crypto_sign`, `agent_call`, `action_call`, `stdout` |
| Вид кода | `inline_code`, `shell`, `script`, `encoded_binary`, `obfuscated`, `unresolved_target` |
| Триггер | `external`, `llm`, `on_import`, `on_install` |
| Ворота | `human_approval` (единственные «сильные»), `confirmation_prompt`, `allowlist`, `budget_limit`, `credential_bound` |
| Вид значения | `literal`, `local`, `derived`, `param`, `untrusted`, `sensitive_local`, `secret` |
| Заявление автора | `read_only`, `local_only`, `no_network`, `no_fs_write`, `credential_bound` |

Высокопривилегированный вызов: `proc_exec`, `code_eval`, `chain_write`,
`crypto_sign`, а `net_write` — только если в него идут недоверенные данные.

## 11 классов находок

| Метка | Что ловит | В нашем чек-листе (`repo-security-review/items/proposed-checklist.md`) |
|---|---|---|
| `dangerous_execution_primitives` | exec/eval на недоверенных данных, на закодированном или обфусцированном коде; **вывод `net_read` сразу идёт в `proc_exec`** | частично (п. 5 «установщики», п. 6) |
| `unverifiable_dependency_source` | исполняется то, что скачано/получено от агента; цель не разрешима (`unresolved_target`) | частично (п. 5) |
| `unsanitized_context_ingestion` | косвенная инъекция: недоверенное значение доходит до привилегированного вызова без `human_approval` | есть (п. 2, цепочка источник → сток) |
| `implicit_egress_channels` | секрет или чувствительные локальные данные уходят наружу через `net_write`/`agent_call` | частично (п. 4) |
| `sensitive_local_resource_overreach` | секрет/чувствительное в действии, где автор его не разрешал; **секрет и недоверенный ввод в одном вызове** | нет |
| `shadow_credentials` | чтение `~/.ssh`, `~/.aws`, env и т. п. **при наличии** канала наружу (без канала — это просто конфиг) | частично |
| `ungated_irreversible_operation` | привилегированный вызов в действии вообще без ворот | есть (п. 3) |
| `hardcoded_c2_communication` | сеть к неразрешимой цели в недоверенной зоне (голый IP, незакреплённый хост) | частично |
| `obfuscation` | обфусцированный или закодированный код | есть (п. 1, 6) |
| `dormant_malicious_payload` | «удалённый рубильник»: привилегированный вызов под условием от недоверенного значения; мёртвый обфусцированный код, до которого нет пути | нет |
| `behavior_claim_contradiction` | автор заявил «только чтение / без сети / локально», а вызов делает запись/сеть | нет |

## Чего нет (граница покрытия)

- **Прямой инъекции в инструкциях скилла** («не говори пользователю»,
  «игнорируй правила», «не спрашивай подтверждения»). Промпт синтеза
  просит записать её в `skill_doc_claim`, но в словаре заявлений такого
  значения нет, и ни одно правило её не использует. Для скиллов это
  главный класс угроз, у нас он в п. 1 чек-листа.
- Хуков, MCP, `bypassPermissions`, широкого `description`, телеметрии
  как отдельных понятий: хук может стать только триггером
  `on_install`/`on_import`, если LLM так решит.
- Социальной инженерии пользователя («скачай zip с паролем и запусти
  до использования скилла»): это не вызов внутри скилла, LLM может его
  не оформить как `proc_exec`. Ровно эта схема — у 21 из 52 образцов их
  же корпуса (см. `prescan-eval.md`).

## Что берём (только идеи, своими словами)

1. Модель «эффект × происхождение данных»: для каждого вызова записать
   эффект из короткого закрытого списка и откуда пришли его входы
   (литерал / параметр / недоверенное / секрет / чувствительное).
   Находка — пересечение, а не наличие эффекта. Это делает п. 2 нашего
   чек-листа механическим.
2. **Ворота различаются по силе.** Только явное одобрение человеком после
   показа входов снимает находку; allowlist, бюджет, «запрос
   подтверждения» — нет.
3. **Чтение секрета — находка только при наличии канала наружу** в том
   же скилле. Снижает шум от «скилл читает свой токен».
4. **Секрет и недоверенный ввод в одном вызове** (ключ API + запрос
   злоумышленника в одном HTTP-запросе).
5. **Заявление против поведения**: сверить, что README/`description`
   обещают («read-only», «без сети»), с найденными эффектами.
6. **Рубильник и мёртвый код**: привилегированный вызов под условием от
   внешних данных; закодированный кусок, на который ничего не ссылается.
7. `unresolved_target` как эпистемическая метка («не можем проверить, во
   что это разрешится»), отдельно от «недоверенное»: голый IP,
   незакреплённый URL, `curl | sh`, `git clone` без SHA, `pip install`
   из `git+`/архива.
