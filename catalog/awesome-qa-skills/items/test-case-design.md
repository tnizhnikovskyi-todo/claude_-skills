## Что делает
Базовый скилл пишет набор кейсов (позитив/негатив/граница) с трассировкой
к требованиям; «plus»-версия добавляет сверку нескольких источников
(«источник А говорит…, Б говорит…»), обязательную матрицу трассировки и
повышенную планку покрытия для высокого риска. Базовый умеет сливать
кандидатов от разных ролей (продукт/QA/UX/тех) в один набор без дублей,
сохраняя список ролей-источников.

## Ценное
- Поля кейса: ID, заголовок, приоритет P0–P3, трасса к ID требования, тип
  (позитив/негатив/граница/регрессия), предусловия, данные, шаги,
  решаемое ожидаемое, заметки (права, очистка, кандидат в автотест).
- Матрица: требование → ID кейсов → какие типы покрыты → пробел. ID в
  матрице обязаны совпадать со списком кейсов.
- Высокий риск: все три типа или явная причина отсутствия; негатив,
  спрятанный в заметках, не считается.
- Ожидаемое без наблюдаемого признака запрещено.
- Дубль-правило: разделять кейсы только при разном триггере, способе
  исполнения или наблюдаемом результате; разная формулировка — не повод.
- Без ID в источнике — стабильная короткая метка с указанием, откуда она.
- Порядок: дымовой → основной → расширенный.
- Самопроверка «вывод неотличим от базового = скилл не применён».

## Слабее нашего / не подходит
Шаблоны вывода общие (Summary/Inputs/Execution/Results); нет ролей Odoo,
групп доступа, многокомпанийности, локализации. «Роли-источники» —
продуктовая команда, не наш случай (у нас один ТР — один источник AC).

## Куда
T11: раздел «Покриття AC» (матрица с колонкой «пробел»), чек-лист перед
выдачей (решаемое ожидаемое, дубль-правило, высокий риск = 3 типа или
причина). `testing`: идея матрицы AC → тест для отчёта о покрытии.
