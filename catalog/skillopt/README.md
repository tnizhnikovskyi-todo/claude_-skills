# SkillOpt (microsoft/SkillOpt)

- **Тип:** Python-фреймворк оптимизации скиллов + плагин для Claude Code (SkillOpt-Sleep)
- **Источник:** https://github.com/microsoft/SkillOpt (★18.9k, MIT, статья arXiv 2605.23904)
- **Версия / коммит:** 0.2.0 (PyPI), `main` @ `bc0a392` (2026-10-29)
- **Дата разбора:** 2026-11-03
- **Вердикт:** **адаптировать идеи** в `skill-feedback` / еженедельное ревью / `evals`; сам инструмент и плагин **не ставить**

## Что делает

Обучает текст скилла как «веса» замороженной модели: модель решает задачи со
скиллом в промпте, другая модель по провалам предлагает ограниченные правки
(не больше N за шаг), правка принимается только если поднимает счёт на
отложенной выборке (validation gate). Есть два применения: исследовательский
цикл на бенчмарках (`skillopt/`) и «ночной цикл» SkillOpt-Sleep по своим
сессиям Claude Code (`skillopt_sleep/` + `plugins/claude-code`).

Гипотеза «автоматическое улучшение текстов скиллов» **подтверждается**, но
только для задач с машинной проверкой ответа: без датасета и грейдера
улучшать нечего. Скиллы, которые ценны действием (спросить до правок, записать
файл, не трогать скилл), их замер (ответ текстом, без инструментов, ≤512
токенов) не видит.

## Какую слабость Claude закрывает

Поправки пользователя и повторяющиеся провалы не превращаются в правила, а
ручные правки скиллов не проверяются на регрессию. Это ровно наш цикл
«замечание → правка → A/B», только у них автоматический и численный.

## Как устроен

- **Оптимизация.** Цель (`target`) отвечает со скиллом; оптимизатор
  (`optimizer`) читает провалы и выдаёт JSON-правки `add/replace/delete` с
  `anchor` и `rationale`; `learning_rate` = максимум правок за шаг (4, по
  косинусу до 2); гейт: кандидат строго лучше на val, иначе отказ; опция
  `gate_no_regression` — ни одна val-задача не просела.
- **Что меряет.** Исследовательский цикл: exact-match / исполнение кода на
  бенчмарках. Sleep: проверки и рубрика, которые LLM-майнер сам пишет по
  транскрипту (`contains`, `regex`, `tool_called`, рубрика → LLM-судья,
  hard при score ≥ 0.8). Сплит train/val = 66/34 по хешу задачи.
- **Модели и API.** Дефолт исследования: Azure OpenAI GPT-5.5 в обеих ролях.
  Sleep: бэкенд `mock` (без сети) по умолчанию; `claude` = `claude -p` без
  инструментов и слэш-команд, модель `sonnet`; также codex, copilot, cursor,
  Azure, OpenAI-совместимые.
- **Стоимость.** Sleep: до 40 задач и 400k токенов за ночь (их учёт
  `len//4` без системного промпта Claude Code, реально больше); порядок
  единиц долларов за ночь на API — оценка, не замер. Исследование: сотни–
  тысячи вызовов на один скилл.
- **Датасет.** Нужен всегда: бенчмарк со сплитами или майнинг из своих
  транскриптов (или ручной `--tasks-file` с `"reviewed": true`).
- **Сеть / телеметрия.** Телеметрии нет. Сеть только к выбранному
  провайдеру. Транскрипты (обрезанные) уходят провайдеру; авторы прямо
  пишут, что очистка от секретов не гарантирована. В коде захардкожены
  внутренние Azure-эндпоинты Microsoft (только для бэкенда `azure_openai`).
- **Плагин Claude Code.** Скилл с широким триггером, хук `SessionEnd`
  (пишет строку в `~/.skillopt-sleep/session-end.log`), cron-расписание,
  установка движка через `pip`/`uv`.
- **Активность.** 593 коммита с мая 2026, 92 автора, CI, сотни тестов,
  последний коммит 2026-10-29.

## Проверка

A/B не делали: по правилам нужен запуск чужого кода и API-бюджет. Сравнение
по устройству:

| Что | Наш цикл (`skill-feedback` + `weekly-review.md` + `claude plugin eval`) | SkillOpt-Sleep |
|---|---|---|
| Откуда замечание | Пользователь поправил → файл в `observations/` | Майнер по транскриптам + английские фразы недовольства |
| Кто правит | `skill-creator` по одобрению человека, отдельная ветка | Оптимизатор сам, ≤4 правила в блок «Learned preferences» |
| Замер | `claude plugin eval` с/без, грейдеры на файлы и инструменты, 3 прогона | Replay текстом без инструментов, гейт на 34% задач |
| Защита от переобучения | «старые кейсы не просели» (по среднему) | Отложенная val-выборка, `gate_no_regression` по каждой задаче |
| Бюджет правки | не ограничен | `edit_budget` 4 правки за раз |
| Учёт отклонённого | `declined` с причиной в наблюдении | список отклонённых правок в отчёте |
| Тип провала | `kind: correction / violation / gap` | `SKILL_DEFECT` (правим тело) / `EXECUTION_LAPSE` (напоминание, тело не трогаем; при сомнении — lapse) |
| Облако | работает (git) | нет: транскрипты и cron эфемерны |
| Приватность | без секретов по правилу, ничего не уходит наружу | куски транскриптов уходят провайдеру |

Вывод: по безопасности и пригодности к скиллам-действиям наш цикл сильнее.
У них есть три вещи сверх нашего, их и берём.

## Что перенести

Всё ниже — правки общих файлов, их делает главная сессия (или задача
`roadmap.md`). Атрибуция: «по мотивам microsoft/SkillOpt (MIT)»,
в `plugins/boost/skills/skill-feedback/references/attribution.md`.

1. **Отложенные кейсы при правке скилла** (`weekly-review.md` §4–5).
   Кейс, написанный по наблюдению, проверяет только «починили»; решение о
   слиянии принимается по кейсам, которые НЕ писались под эту правку
   (существующие `evals/<skill>/*` + `general/`). Так уже устроен
   оптимизатор описаний в `skill-creator` (`run_loop.py`: 60/40, лучший по
   test), но не наш процесс правки тела скилла.
2. **No-regression по каждому кейсу**, а не по среднему (`weekly-review.md`
   §5): если любой старый кейс просел больше разброса между прогонами,
   правку не сливать. Обоснование — `docs/sleep/RESULTS.md` §1: без гейта
   0.554 → 0.026 за 5 итераций, с гейтом без потерь.
3. **Бюджет правок** (`weekly-review.md` §4): за одно ревью у скилла не
   больше ~4 изменённых правил, каждое в форме «op / anchor / новое
   правило / почему». Отклонённые A/B правки записывать в `resolution`
   наблюдения, чтобы их не предлагали снова.
4. **Нарушение vs дефект** (`skill-feedback`, `format.md`). Вопрос
   классификации из `skill_aware.py`: «есть ли в скилле правило, которое,
   если ему следовать, предотвращает ошибку?» Да → `kind: violation`
   (текст не трогаем; при повторе — барьер), нет → `gap`. При сомнении —
   `violation`. У нас поля есть, нет теста и правила по умолчанию.
5. **Не переносить грейдер в скилл** (правило для `skill-creator`-правок в
   `weekly-review.md`): правка формулирует поведение («укажи URL
   источника»), а не текст проверки (regex, строку из грейдера). Иначе
   скилл учится проходить кейс, а не делать работу.
6. **Русские фразы недовольства** как подсказка для поиска замечаний
   (опционально, решение пользователя): «не то», «опять», «переделай»,
   «неправильно», «я же просил». Главная сессия могла бы раз в неделю
   смотреть свои облачные сессии через `list_events` и предлагать
   наблюдения. Цена и приватность не оценены, в `parked`.

Не брать: сам плагин и `pip install skillopt` (не работает в облаке, шлёт
транскрипты провайдеру, широкий триггер, второй писатель в `CLAUDE.md`
рядом с `cloud-memory`); обученные скиллы из `ckpt/` (подгонка под
exact-match бенчмарков, 300–2000 слов).

## Риски и заметки

- Безопасность 1, а не 0: по умолчанию `mock`, staging и ручной `adopt`,
  отправка данных честно задокументирована. Но на рабочих сессиях с
  клиентскими данными запускать нельзя.
- Реальный прогон, если понадобится: только `mock` или `--tasks-file` с
  синтетикой, в отдельном каталоге, с разрешения пользователя.
