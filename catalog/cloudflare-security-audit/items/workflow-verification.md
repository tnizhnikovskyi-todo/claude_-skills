# Процесс: 6 фаз и независимая проверка

Файлы: `skills/security-audit/SKILL.md`, `RECONNAISSANCE.md`, `HUNTING.md`,
`VALIDATION-AND-REPORTING.md` @ `c1c8a8c` (MIT, Cloudflare).

## Как устроено

Два режима. **Guidance** (по умолчанию): на вопрос о безопасности или точечное
ревью берутся только нужные части, файлы не создаются. **Full audit**: только по
явной просьбе «аудит / пентест / полный разбор / нужны отчёты»; если неясно —
один вопрос.

| Фаза | Кто | Что |
|---|---|---|
| 1. Разведка | 4 параллельных `research`-агента (продукт и сборка; принципалы и контроли; входы и стоки; что можно проверить локально) | `architecture.md` (≤1000 слов) и `coverage-ledger.json`: единица = вход × граница доверия × подсистема × класс атаки |
| 2. Охота волнами | охотник на единицу/группу единиц; после волны свежий **критик покрытия** | охотник возвращает JSON (covered / candidate / blocked + проверки); критик ищет непокрытые входы, параллельные пути, необоснованные исключения → новая волна |
| 3. Проверка кандидатов | свежий верификатор на каждый кандидат, не охотник | «Ты не писал этого кандидата. Попробуй опровергнуть»; перечитывает каждую строку trace, восстанавливает сильнейший контроль, сам воспроизводит результат (только в песочнице) → `confirmed` / `needs_validation` / `rejected` |
| 4. `findings.json` | родитель | схема с `additionalProperties:false`, два валидатора на Node |
| 5. Проверка записей | ещё один свежий верификатор на каждую финальную запись | `verified` или `replace`; существенная замена → третий верификатор |
| 6. Отчёты | родитель | `REPORT.md`, `FINDINGS-DETAIL.md`, `NEEDS-VALIDATION.md` только из проверенных записей |

Профили `quick` / `standard` / `deep` меняют ширину, но не планку доказательств.
Повторные прогоны аддитивны: прошлые ledger и findings читаются, неизменённый
`confirmed` переносится с перепроверкой, `rejected` гасит только ту же
неизменённую претензию, а не покрытие единицы.

## Чем отличается от нашего `independent-check` (отклонён, Δ=0)

| | `independent-check` (наш) | их фаза 3/5 |
|---|---|---|
| Что проверяет | своё решение/ответ целиком | каждого кандидата по отдельности |
| Цель | найти ошибку в выводе | **опровергнуть** находку (фильтр ложных) |
| Вход | задача + решение | только кандидат, его проверки, нужные факты архитектуры; без выводов других |
| Новые факты | нет, перечитывание | да — локальный прогон в песочнице |
| Масштаб | 1 ответ | десятки кандидатов по всему репо |

Основание перепроверить наш вывод есть только в одном месте: **фильтр ложных
срабатываний на полном аудите модуля**, где кандидатов много. На наших дифах
`td.*` (фикстуры S1–S3) кандидатов 1–3, базовый скилл уже 13.5/15, а раздувание
severity (S2, вариант A: 4 VULN) закрыли состояния закрытия Strix за +15 % токенов.
Исполнять код у нас негде по их же правилам (нет OS-песочницы без сети с
лимитами) → верификатор только перечитывает → ожидаем Δ≈0 при цене ×N.

**Вывод:** `independent-check` не переоткрывать. Если делать опыт — узкий:
опровергающий верификатор только для кандидатов `VULN` в **полном** аудите
модуля (не диффа), 0–2 вызова на прогон.

## Что полезнее верификатора — критик покрытия

Свежий агент получает не находки, а ledger и ищет, что не проверено. Их довод:
«один прогон нашёл примерно половину того, что нашли повторные» (README,
без методики и цифр). У нас тот же эффект дешевле **барьером**: перед APPROVE
каждая строка диффа с `@http.route`, `sudo()`, `cr.execute`/`SQL(`, `Markup(`,
новым `_name`, правкой `ir.model.access.csv`/`ir.rule`/`groups=` обязана быть
строкой таблицы покрытия. Это можно сделать grep-ом без агента (принцип
«второе нарушение → барьер»).

## Что не берём

- 11-шаговую процедуру переноса артефактов (`fstat`, no-follow), повторённую
  дословно в 3 файлах: у нас нет исполнения кода цели.
- Бюджет агентов, резервы критиков, percent-encoding `coverage_id`.
- Двойную проверку записей (фазы 3 + 5) — дорого, у нас Δ не ожидается.

## Оценка (как метода для нас)

| Критерий | Балл | Комментарий |
|---|---|---|
| Прирост | 1 | Сверх нашего: критик покрытия (как барьер), повторный аудит по fingerprint |
| Частота | 1 | Полный аудит модуля — редко; ворота диффа — наши |
| Надёжность | 2 | Чётко прописано, но очень длинный протокол, evals не опубликованы |
| Стоимость контекста | 0 | ×15–20 к нашему прогону (оценка) |
| Безопасность | 3 | Только текст, строгие правила исполнения |
| Поддержка | 3 | Cloudflare, активен |
| **Итого** | **10/18** | Процесс не берём; две идеи — адаптировать |
