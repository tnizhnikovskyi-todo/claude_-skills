# cloudflare-security-audit — summary для главной сессии

**Что это.** Скилл `security-audit` от Cloudflare (MIT по `LICENSE`, ★58k, активен, разобран `c1c8a8c`): 6 фаз полного аудита репо — разведка 4 агентами, охота волнами по ledger покрытия с критиком покрытия, свежий верификатор-опровергатель на каждого кандидата, `findings.json` по строгой схеме (confirmed / needs_validation без severity / rejected) + 2 валидатора на Node, второй верификатор на каждую запись, отчёты. Код цели исполняется только в OS-песочнице. Только текст, без хуков, MCP и сети.

**Независимая проверка ≠ наш `independent-check`.** У них опровергатель работает по ширине (десятки кандидатов на весь репо) и может исполнять проверку в песочнице, то есть приносит новые факты. У нас песочницы по их же правилам нет → верификатор будет только перечитывать → ожидаем Δ≈0 при цене ×N. Отказ `independent-check` не пересматриваем; узкий опыт возможен только для `VULN` в полном аудите модуля.

**Лучшие находки для Odoo 19** (`items/attack-classes.md`):
1. 12 вопросов из классов Access control / Business logic / Feature abuse / Data isolation, из них 7–8 у нас нет: поле в теле `write` перебивает права (`company_id`, `state`), пакетные `export_data`/`load`/отчёты под `sudo()`, `action_*` по RPC в «не том» `state`, `access_token`/`ir.attachment`, `active_test=False`, `search_count`/`read_group` как оракул.
2. Различитель high/medium («полностью снимает явный контроль или ослабляет») и «defense-in-depth / self-impact — не находка».
3. Критик покрытия → у нас дешевле как **барьер**: каждая строка диффа с `route`/`sudo()`/`cr.execute`/ACL/`ir.rule` обязана быть в таблице покрытия.
4. Повторный аудит после правок по fingerprint (закрыт / остался / новый); план закрытия пробела «локально / на инстансе».
