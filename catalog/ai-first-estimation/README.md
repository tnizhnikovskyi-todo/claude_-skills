## Что делает

Оценивает проект, в котором весь код пишут ИИ-агенты, и считает только
«чистое время человека»: постановку задачи, выдачу доступов, продуктовые
решения, смоук-тесты на проде, приёмку и надзор за агентом. Принцип: часы
человека растут не с объёмом кода, а с числом **точек касания с реальным
миром** (живые деньги, доступы, ревьюеры магазинов, необратимые действия,
решения). Выход: таблица `Модуль | Часы человека | Роль человека`, диапазон,
отдельно «несжимаемое ядро», урезанный вариант под открытые вопросы,
исключения и обязательные условия оценки. Подробно:
[`items/ai-first-estimation.md`](items/ai-first-estimation.md).

## Какую слабость Claude закрывает

Без указаний модель оценивает AI-сборку по привычкам «до ИИ»: часы на
написание кода, лишние задачи «по best practice», запас на воображаемую
сложность. Скилл переводит оценку на один вопрос: «что здесь делает
человек?». Это проблема и для нас: сборку MVP ведёт Claude
(`odoo19-mvp-build`), а таблица «Обсяг робіт» в наших ТР всё ещё по этапам
разработки (см. ниже).

## Как устроен

`SKILL.md` ~5,6 КБ (~1,4 тыс. токенов), грузится по вызову. Скриптов, хуков,
сети, прав нет. Ставки нет (задаётся при вызове). 4 коммита за один день,
★1, после 2026-08-08 изменений нет.

## Сравнение с нашими скиллами

**Ограничение:** тексты `odoo19-tr-authoring:tr-effort-instruction` и
`odoo19-sales-prep:preliminary-estimate` в этой среде **недоступны**
(`~/.claude/plugins/synced/` пуст). Сравнение по форме выхода
`tr-effort-instruction` в готовых ТР (внутренняя база, клиентские данные сюда
не переносим) и по соседним карточкам. Пункты «у нас нет» **сверить с
оригиналами** перед правкой.

Что видно по выходам `tr-effort-instruction`: таблица «Обсяг робіт»
`Етап | План люд./год. | Коментар` с этапами *Технічне рішення / Архітектура
/ Розробка / Тестування / Інструкція*, значения вилкой. Скилл умеет
отказаться от оценки, пока открыты вопросы клиенту. `preliminary-estimate`
по соседним карточкам даёт вилку с коэффициентом.

| Тема | ai-first-estimation | Наше | Итог |
|---|---|---|---|
| Единица оценки | Часы человека по модулю + **роль человека** | Часы по этапам (Розробка, Тестування…) | **Брать**: при AI-сборке строка «Розробка» непонятно чья — человека или проверка работы Claude |
| Обоснование чисел | Нет никакого | Неизвестно (сверить) | Ничего не берём |
| Открытые вопросы | Урезанный вариант с условием-триггером | Отказ от оценки до закрытия вопросов | **Брать** как промежуточный шаг: вилка «если ответ А / если Б» вместо отказа |
| Несжимаемые блоки | Платежи, магазины, E2E, PM | Не видно | **Брать идею**, список свой (Odoo) |
| Изменение требований | Явное условие: = повторная проверка = часы | `tr-change-request` есть, но условия в оценке не видно | **Брать** в условия оценки |
| Календарь | Отдельно от часов, критический путь — клиент | Не видно | Брать |
| OPEX ИИ | Токены — отдельно, не разработка | Не видно | Решить на уровне коммерции |
| Ревью кода | Только точечный аудит денег/ПДн | Гейты `pr-review`, `security-review` на всё | **Мы сильнее**, их подход не брать |
| Доменные точки касания | B2C: KYC, пуши, App Store | ERP: миграция, UAT, обучение, фискализация | Наш список писать заново |

## Риски и заметки

- Перед правкой наших скиллов **прочитать их оригиналы**: часть пунктов
  «у нас нет» может уже быть в тексте (принцип №28).
- Без данных о факте часов любые коэффициенты останутся догадкой. Полезнее
  сначала собрать факт по 5–10 ТР, собранным через `odoo19-mvp-build`:
  сколько человек реально тратил на постановку, ревью, UAT.
- Переход на «часы человека» меняет коммерческую модель (что продаём
  клиенту) — это решение руководства, а не правка скилла.
