# Strix: координация агентов и общее состояние

- **Тип:** паттерн оркестрации (промпт + инструменты `threat_model`, `coverage`, `notes`, `agents_graph`, `reporting`)
- **Источник:** `strix/agents/prompts/system_prompt.jinja`, `strix/tools/{threat_model,coverage,notes,reporting,agents_graph}`, `strix/skills/coordination/*`
- **Версия / коммит:** `6b7ae2e`
- **Дата разбора:** 2026-11-02
- **Вердикт:** адаптировать идеи (для многоагентных ревью через `workflow-authoring` / субагентов)

## Что делает

Как Strix не даёт десяткам агентов терять контекст и дублировать работу:

1. **Корень только оркестрирует.** Явный запрет корню трогать цель
   («даже один быстрый тест — делегируй»). Время корня: скоуп,
   декомпозиция, запуск/мониторинг детей, todo/notes/coverage, итог.
2. **Один агент = один класс уязвимости × один компонент**, 1–5 скиллов,
   «никаких агентов-универсалов». Цепочка на находку:
   Discovery → Validation (отдельный агент доказывает PoC) → Reporting
   (+ фикс в том же шаге, без отдельного «fixing agent»).
3. **Общая модель угроз** (`get/save/amend_threat_model`). Обязательные
   разделы: overview, trust boundaries, attack surface, severity
   calibration. Каждый агент сначала читает её, а опровергнутые
   предположения дописывает поправками: «модель, которую никто не
   правит, превращает догадки первого агента в допущения всех».
4. **Coverage ledger** (`record/update/list_coverage`): строка на
   поверхность × риск с исходом `reported` / `ruled_out` /
   `needs_follow_up` / `no_issue_found` / `not_applicable` и обязательным
   evidence. Перед финишем корень обязан разобрать все `needs_follow_up`.
   Цель: отличать «проверено и чисто» от «не смотрели».
5. **Отчёт как структурированный объект** с валидацией полей
   (counterevidence, confidence, severity_change_conditions, http_exchange_ids,
   code_locations с `fix_before/fix_after`, fix_verification), LLM-дедупликацией,
   правкой (`update_vulnerability_report`) и удалением опровергнутого
   (не оставлять «retracted» отчёты).
6. **Notes** — общий блокнот для фактов, которые не находка и не
   покрытие (рабочие креды, инвентарь эндпоинтов).

## Что взять

- Для наших многоагентных ревью (если будем делать workflow
  «security-review по компонентам»): схему «discovery → независимая
  валидация», общий threat model файлом, coverage-таблицу в итоговом
  отчёте.
- Даже в одноагентном `security-review`: начинать с короткой модели
  угроз модуля (кто атакующий: портальный пользователь / внутренний
  пользователь другой компании / публичный контроллер; границы доверия;
  что считается critical) и заканчивать таблицей покрытия.

## Оценка

| Критерий | Балл (0–3) | Комментарий |
|---|---|---|
| Прирост | 2 | Coverage и threat model — то, чего нет в нашем выводе ревью |
| Частота | 2 | Модель угроз + покрытие — в каждом ревью; многоагентность — реже |
| Надёжность | 2 | Механизмы продуманы (валидация полей, запрет дублей), у нас не испытаны |
| Стоимость контекста | 2 | Идеи компактны; полная многоагентная схема дорогая |
| Безопасность | 3 | Перенос идей, без кода |
| Поддержка | 3 | Активно |
| **Итого** | **14/18** | |

## Риски и заметки

- Требование «2000+ шагов минимум», «попробуй ещё 10 подходов» — это для
  автономного пентеста с бюджетом, не для нашего ревью.
