- **Вердикт:** **адаптировать** — главная ценность всего репозитория для нас

## Что делает

Пять текстов (~760 строк), которые задают дисциплину рассуждения агента
при поиске уязвимостей. Не привязаны к Docker или инструментам: работают
и для чистого статического ревью, то есть подходят прямо в наш
`security-review`.

| Файл | Строк | Суть |
|---|---|---|
| `counterevidence.md` | 191 | Три состояния закрытия кандидата; что НЕ является доказательством безопасности; проход «аргументируй против» перед отчётом |
| `severity_calibration.md` | 130 | Рубрикатор critical/high/medium/low, список «обычно НЕ high», чек-лист приёмки high/critical, «понижай, не удаляй» |
| `source_aware_discovery.md` | 216 | Дисциплина перечисления: одна причина ≠ один кандидат; где на самом деле живёт контроль; «семейные» обходы (десериализация, архивы, outbound-запросы, auth state machines, SAML, self-service update) |
| `fix_verification.md` | 129 | Порядок оценки фикса и 5 ворот: применимость, закрытие, обход, сохранение поведения, проверки репозитория; когда фикс не предлагать |
| `scan_modes/diff.md` | 94 | Что в скоупе PR-ревью: новая достижимость старого синка, ослабленный общий хелпер, удалённый контроль, сменённое умолчание; «читай код, не описание PR» |

## Какую слабость Claude закрывает

- **Тихое отбрасывание.** «Похоже, ORM экранирует / middleware защищает»
  без проверки конкретного пути. Strix требует назвать контроль, место и
  показать, что он выполняется на каждом пути атакующего ДО синка.
  Иначе кандидат остаётся `open_proof_gap`, а не исчезает.
- **Безопасный сосед как алиби.** Один правильно защищённый вызов не
  закрывает остальные.
- **Схлопывание.** Шесть мест одного хелпера → одна «находка» → пять
  остаются неисправленными.
- **Завышение severity.** Тест «примет ли это серьёзный триаж bug bounty?»
  + чек-лист из шести пунктов.
- **Фикс, который закрывает только наш payload.** Ворота «bypass review»:
  перечитать без опоры на собственную логику, попробовать другой класс
  входа (кодировка, content type, другой HTTP-глагол).
- **Ревью PR по описанию.** Описание PR — недоверенный ввод.

## Что конкретно перенести в наш `security-review`

1. В формат каждой находки: `counterevidence`, `confidence` (+ обоснование;
   статика без исполнения ≤ medium), `severity_change_conditions`.
2. В итог ревью: список закрытых областей с указанием контроля
   (`ruled_out`) и отдельный список `open_proof_gap`. Сейчас APPROVE не
   говорит, что именно проверено.
3. Блок «Что НЕ доказывает безопасность» — почти дословно, это 30 строк.
4. Чек-лист high/critical — перед BLOCK.
5. Правила diff-скоупа — для ревью PR в `odoo19-mvp-build`.
6. Ворота проверки фикса — для «concrete fixes» в выводе Odoo-ревью.

Odoo-переложение «где живёт контроль» (своё, не из Strix):
`sudo()` / `with_user()` / `check_access_rights` / record rules
(`ir.rule`) / `auth='public'` и `csrf=False` в контроллерах / `search()`
без domain по компании / `_sql` с форматированием строк / `t-raw` /
`safe_eval`. «Семейный обход»: нашли один `sudo()` без проверки
владельца → пройти все методы того же модели и все контроллеры, которые их
вызывают.

## Риски и заметки

- Тексты местами шаблонизированы Jinja (`{% if coverage_tools %}`): при
  переносе вычищать.
- Лицензия Apache-2.0: при дословном переносе указать источник и
  сохранить NOTICE/атрибуцию.
- Методология рассчитана на агентов с бюджетом в тысячи шагов; для
  нашего ревью брать принципы, а не требования «обязательно запусти
  semgrep + gitleaks + trivy + ast-grep».
