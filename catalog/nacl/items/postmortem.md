# Постмортем «какой скилл пропустил баг» (`nacl-postmortem`)

- **Источник:** `nacl-postmortem/SKILL.md` (100 строк), `.claude/workflows/nacl-postmortem-panel.js`, `gate-fire-catalog.md` (G1–G11), `project-gap-closure.md` (10 категорий GAP)
- **Вердикт:** адаптировать (как режим нашего цикла `skill-feedback` / еженедельного ревью)

## Что это

Ретроспектива проекта, собранного скиллами. Берутся коммиты-исправления
после границы «разработка → фиксы». Для каждого бага:
- найти спеку и **дословно** её процитировать;
- классифицировать: `SPEC_WRONG` / `SPEC_MISSING` / `SPEC_RIGHT_DEV_DRIFTED`;
- указать, какой скилл и какие ворота должны были его поймать.

Сопоставление «категория → скилл» задано таблицей, а не решением агента.
То, что не сопоставилось, честно помечается `unmapped`. Отдельный аудитор
ищет межфичевые связи («UC-X объявляет вход, а у UC-Y нет кнопки»).
Цитаты перепроверяются по файлам. Скиллы в этом отчёте не правятся,
только рекомендации.

Вариант workflow: 5 параллельных аудиторов, проверка, синтез и писатель,
~8–12 агентов. Есть и ручной рецепт.

## Перенос к нам

У нас есть `boost:skill-feedback` и папка `observations/`: «ожидали /
получили / предложение». Постмортем закрывает обратную сторону: баги,
которые клиент нашёл после сдачи MVP. Предложение:
- режим «ретро после MVP»: вход — список багов/правок после приёмки
  (тикеты, коммиты `fix:`) и ТР + SPEC.md проекта;
- на каждый баг: цитата из ТР/SPEC, класс (ТР неверно / в ТР нет /
  разработка отошла от ТР), какой наш скилл должен был поймать
  (`tr-usecases-acceptance`, `tr-odoo-tech-design`, `tr-review`,
  `pr-review`, `testing`), запись в `observations/`;
- таблица «класс → скилл» фиксированная, не сопоставилось — `unmapped`.

Ручной рецепт, без workflow. Workflow включать только по явной просьбе
(цена, `synthesis.md` п. 5).
