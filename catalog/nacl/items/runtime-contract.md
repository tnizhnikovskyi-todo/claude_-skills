# Runtime Contract (`nacl-sa-uc`, Phase 4.5)

- **Источник:** `nacl-sa-uc/SKILL.md`, раздел «Phase 4.5: Runtime Contract» + `references/runtime-contract.cypher`; ворота G8 в `nacl-tl-core/references/gate-fire-catalog.md`
- **Вердикт:** адаптировать (текст, без графа)

## Что это

Для UC с длительным или асинхронным состоянием спека обязана описать
не только «что происходит», но и устойчивую машину состояний. Без этого
типы и артефакты сходятся, а рантайм нет. Метод выведен из двух
постмортемов автора:
- «Рестарт упавшей задачи» возвращал 200, а задача оставалась `failed`
  (`INSERT … ON CONFLICT DO NOTHING` молча гасил повторную постановку).
- «Cancel во время fail»: без блокировки строки выигрывала случайная из
  двух записей.

**Когда обязателен** (дерево решений, любое из):
1. В шагах есть queue / worker / async / job / poll / cron / retry / cancel.
2. Сущность имеет `status` / `state` / `phase`.
3. Внешний провайдер асинхронный.
4. Требование содержит retry / restart / cancel / recover / idempotent.
5. Зависимость от UC-воркера или планировщика.

Если не обязателен, это фиксируется явно (`not_required`). Если обязателен
и не заполнен, статус `BLOCKED`.

**8 обязательных полей:** машина состояний (состояния и переходы); граница
транзакции на переход; стратегия блокировки; события с жизненным циклом
pre-/post-commit; политика повторов с ограничением; кто выигрывает в
гонке «cancel во время X»; процедура восстановления после падения
процесса; ключ идемпотентности (`ON CONFLICT DO NOTHING` ключом
не считается).

## Перенос к нам

Это блок «Контракт виконання» в `tr-odoo-tech-design` (Крок 2) и пункт
в `tr-review`. Нужен для моделей с полем `state` (Selection), кнопками-
переходами, `ir.cron`, интеграциями (вебхуки, внешние API).

Перевод полей на Odoo. Конкретные API проверять через `source-check`
по Odoo 19, по памяти не писать:

| Поле NaCl | В ТР для Odoo |
|---|---|
| FSM | Таблица `state`: значение → кнопка/метод → новый `state` → кто может; недопустимые переходы → `UserError` |
| Txn boundary | Переход в одном вызове ORM (одна транзакция запроса); где cron/батч делает промежуточные commit — указать явно |
| Lock | Что защищает от двойного нажатия и параллельного cron (блокировка строки / проверка `state` под блокировкой) — UNVERIFIED-API |
| Events pre/post commit | Письма, `bus`, вызовы внешних API — после commit (механизм postcommit — сверить с docs 19) |
| Retry | Сколько повторов cron/интеграции, с каким интервалом, что после лимита (статус ошибки, активность) |
| Cancel race | Что если «Скасувати» нажали, пока cron обрабатывает запись |
| Recovery | Что с записями «в обработке» после падения воркера / рестарта сервера |
| Idempotency | Чем повтор вебхука/импорта не создаёт дубль: `external_id`, SQL-ограничение `unique`, проверка перед `create` |

**Граница покрытия:** не проверяет производительность и не заменяет тесты.
Только заставляет ТР ответить на 8 вопросов.

## Проверка, которую предлагаю

Фикстура ТР: модель «Заявка на синхронізацію» со `state` и cron,
обмен с внешним API. `tr-review` с пунктом и без. Метрика: найдены ли
«нет перехода error → draft», «дубль при повторе вебхука», «cron и
кнопка одновременно».
