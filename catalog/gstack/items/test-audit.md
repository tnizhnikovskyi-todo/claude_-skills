# test-audit (планка ценности теста)

- **Тип:** скилл
- **Источник:** `test-audit/SKILL.md@7caca33` (раздел «Boundaries», шаги 2–3), `docs/test-value-bar.md`
- **Лицензия:** MIT
- **Вердикт:** адаптировать планку и «карточку ценности» в `odoo19-mvp-build:testing` и `pr-review`; сам скилл аудита — нет

## Что делает

Ищет малоценные и дублирующие тесты и тестовый код, который они держат.
Ядро — **планка ценности**: тест пишется, только если есть все 4 ответа:
1) какое наблюдаемое поведение/инвариант/контракт он защищает;
2) какая правдоподобная регрессия его уронит; 3) почему существующие
тесты это не ловят (лучше строка в табличном тесте, чем почти-дубль);
4) нужен ли продуктовый «шов» только ради теста (если да — тестировать на
настоящей границе). Однострочная карточка:
`Value: protects=…; fails_when=…; why_new=…; seam=none; no_claim=…`,
где `no_claim` — что зелёный тест НЕ доказывает (что замокано).

Каталог малоценного: тесты без assert, сравнение с собой, копии фикстур,
grep по исходнику, тесты приватного предиката при наличии теста границы,
продуктовый код, который вызывают только тесты. Регрессионный тест
обязан упасть на HEAD до правки, пройти на базе и после правки.

## Какую слабость Claude закрывает

Модель пишет много тестов «для покрытия», тавтологичные и с моками
вместо границы, и не говорит, что зелёный тест не доказывает. Это наш
RH-5 из `gate-integrity` с другой стороны: не ловить, а не писать.

## Сравнение

`odoo19-mvp-build:testing` (по описанию: генерация тестов по AC) и наш
`pr-review` (мутации, Prove-It). Карточки ценности и строки `no_claim`
нет ни там, ни там. Для Odoo `no_claim` особенно полезен: `TransactionCase`
с `sudo()` не доказывает права, `Form` не доказывает JS-виджет, мок
внешнего API не доказывает интеграцию.

## Что взять

Пересказом: 4 вопроса + карточку `protects / fails_when / why_new /
no_claim` — в шаблон теста `testing`; в `pr-review` — проверка «у нового
теста есть карточка, `no_claim` не пуст». Механический префильтр
(grep без assert, хэш почти-дублей) — как идея для `repo-audit`.

## Проверка (план)

Кейс: AC с проверкой прав; без вставки модель пишет тест под `sudo()` и
считает права проверенными. С вставкой — `no_claim=права (тест под sudo)`
или тест под `with_user`. Плюс негатив: тривиальный AC — без раздувания.
