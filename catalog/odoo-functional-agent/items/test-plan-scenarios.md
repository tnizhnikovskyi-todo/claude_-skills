# «Test plan» и сценарии

- **Источник:** `skills/odoo-functional/plan_md_template.md` («Test plan», «Test identities»),
  `skills/odoo-functional/SKILL.md` Phase 6, 8, `docs/scenario_format.md`,
  `docs/plan_format.md` «Test identities» @ `084b690`
- **Вердикт:** адаптировать в `odoo19-mvp-build:testing` и T11 `uat-test-book`

## Что делает

- **Test plan в плане, до одобрения.** Каждая потребность требования — строка:
  сценарий и что он проверяет (поля и ожидаемые значения; для негатива — класс
  исключения и текст). Не проверяемое — **Not tested** с причиной; потребность
  нельзя выбросить. Отчёт и экспортированный файл тестируются (`check`), «посмотреть
  в UI» не принимается без попытки.
- **Отчёт сравнивает с одобренным Test plan:** каждая ослабленная/выброшенная
  проверка, добавленный/разбитый сценарий, переход в Not tested — с причиной.
- **Роли.** Все шаги по умолчанию идут под `ofa_bot` — админом, который пропускает
  согласования. Поэтому роль (покупатель без права одобрения, пользователь одной
  компании) задаётся отдельной операцией плана на тест-пользователя
  `ofa_user_1..3`: `group_ids`/`company_ids` только через `$set`; админ-группы
  (`base.group_system`, `base.group_erp_manager`, в т.ч. через implied) запрещены
  и проверяются до и после записи. На реальной базе таких пользователей нет —
  эти операции не переносятся.
- **Негативные тесты** — шаг с `expect_error`: класс исключения Odoo + текст,
  скопированный из исходника 20.0 или из прогона, не угаданный. Шаблонный текст
  (подставляются модель/операция) не заполнять самому: какой check откажет первым,
  тот и решает текст. После отказа — прочитать, что ничего не изменилось.
- **Нельзя** править ожидания, чтобы fail стал pass; исправленный сценарий
  перезапускать целиком, при коллизии — на свежей базе.
- **Мультикомпания:** без `company` сценарий читает значения в компании бота
  по умолчанию (их пример: `total_due` = 0 вместо 133 980 MXN).

## Что сверх нашего

Это проверяемая дисциплина «каждая потребность → доказательство или явное Not
tested», роли не под админом и негативы с текстом из источника. Для `uat-test-book`
и `testing` ценнее всего три правила: роль ≠ админ, негатив с точным текстом,
расхождения с одобренным планом тестов в отчёте.

## Перенос на 19.0

`res.users.group_ids`/`all_group_ids` в 19.0 те же (`odoo/addons/base/models/res_users.py:257-258`
@ 19.0). Права в 19.0 — `ir.model.access` и `ir.rule`, не `ir.access` (20.0).
