**Важно для облака.** Сервер и линтер опираются на исходники Odoo на диске
(ищет `~/odev/worktrees/<ver>`, `~/odoo/<ver>` и т.п.). Без них модель
считается «не закрытой»: проверки неизвестных полей/методов молчат или
понижаются с пометкой *unverified*. В нашей облачной сессии исходников
Odoo нет → остаются в основном правила версий и манифеста. Плюс нужен
LSP-инструмент Claude Code и конфликт с `pyright-lsp` по `.py`.

**Сверка с исходниками Odoo (скачали `odoo/orm/models.py`,
`odoo/orm/model_classes.py` из ветки 19.0 и `odoo/models.py` из 18.0):**
- ✅ В 19.0 `_inherit` строкой даёт `_name` = эта строка; `_inherit`
  **списком без `_name`** — имя модели выводится из имени класса
  (`MileageKpi` → `mileage.kpi`) с warning в лог. В 18.0 список из одного
  элемента без `_name` давал `_name = inherit[0]`, т.е. расширение.
  odoo-lens это правило знает.
- ✅ В 19.0 `_check_inherits` требует явно объявить Many2one-поле для
  `_inherits` (иначе ошибка с подсказкой `required=True, ondelete='cascade'`).
  В 18.0 поле создавалось автоматически.
- Остальные правила версий (переименования полей `res.groups`, `auto_join`,
  `@api.returns`, `name_get` и т.д.) взяты из кода odoo-lens и **не сверены**
  с документацией — пометка UNVERIFIED в `items/linter-rules.md`.

**Находка про наш `boost:odoo-model-map`.** Скрипт `odoo_map.py`
(стр. ~119–129) при отсутствии `_name` и `_inherit` из одного элемента
считает класс расширением — это поведение ≤18. Под Odoo 19 `class
MileageKpi: _inherit = ['td.vehicle']` создаёт НОВУЮ модель `mileage.kpi`.
Тот же пример стоит в `SKILL.md` (строка ~20) как расширение, и фикстура
eval `_fixture/addons/td_fleet_report/models/kpi.py` + кейс `who-extends`
закрепляют неверную для 19 семантику. Нужна правка (см. README, раздел
«Что перенести»). Чужие файлы не трогали — правку делает главная сессия /
сессия реализации.
