# odoo-lens

- **Тип:** плагин Claude Code (LSP-сервер + линтер модулей + скилл + хук `SessionStart`)
- **Источник:** https://github.com/ChengyanOo/odoo-lens (★21, **лицензии нет**)
- **Версия / коммит:** `2482f92` (2026-10-22) = HEAD на 2026-11-03, плагин `0.1.0`
- **Дата разбора:** 2026-11-03
- **Вердикт:** **адаптировать** (правила линтера → наши чек-листы; поправить
  `odoo-model-map`). Сам плагин не ставить.

## Что делает

Python-сервер (только stdlib, ~17 тыс. строк кода + ~10 тыс. тестов) для
Odoo 16.0–20.0 включая saas-19.x. Индексирует исходники Odoo и кастомные
модули так, как Odoo их грузит, и отдаёт Claude через LSP-инструмент
hover, переходы к определению/переопределениям, ссылки (Python, XML, CSV,
JS), поиск символов, иерархию вызовов. Отдельно — линтер
`odoo-lens check <модуль>`: неизвестные модели/поля/методы/xml-id с
«did you mean», недостающие `depends`, неимпортированные файлы, кнопки на
`_`-методы, синтаксис, удалённый в версии модуля. Хук на старте сессии
подсказывает Claude пользоваться им вместо grep.

Гипотеза «линтер/LSP для Odoo 16–20» подтвердилась.

## Какую слабость Claude закрывает

1. **Odoo-связи в строках и XML** — то, на чём споткнулись serena и
   graphify: odoo-lens знает `_inherit`/`_inherits`, вью и xml-id.
2. **Порядок переопределений** (`super()` через несколько модулей) —
   grep этого не даёт, наш `odoo-model-map` тоже.
3. **Устаревший API по версии** — модель пишет код «под 16–17» в модуле 19.

## Как устроен

- `.lsp.json`: сервер `bin/odoo-lens` на `.py/.xml/.csv/.js`.
- `skills/odoo-lens/SKILL.md` (~5.9 КБ): какую LSP-операцию брать под какой
  вопрос, синтаксис запросов `model:`/`view:`/`field:`…, «сначала линтер».
- `hooks/hooks.json`: `SessionStart` → `odoo-lens session-hint` (~50 мс):
  если в проекте Odoo-код, одна подсказка в контекст; иначе тишина.
- Индекс в пуле процессов, кэш `marshal` в `~/.cache/odoo-lens`; Odoo 20
  community+enterprise: 4–5 с холодный старт, ~470–700 МБ памяти.
- Исходники ищет сам (`~/odev/worktrees/<ver>`, `~/odoo/<ver>`…) или по
  `.odoo-lens.json`. **Без исходников** проверки по моделям молчат или
  понижаются с пометкой *unverified*.
- Сеть, телеметрия, `subprocess`, `eval` — не найдены (grep по всему коду).

### Находка: наш `odoo-model-map` неверно читает `_inherit` списком в Odoo 19

Сверено по исходникам Odoo (`odoo/orm/models.py` в 19.0 против
`odoo/models.py` в 18.0): в 19.0 `_inherit = ['x']` без `_name` даёт модель
с именем **из имени класса** (warning в логе), а не расширение `x`. В 18.0
это было расширение. Наш `odoo_map.py` (блок определения `role`) и пример в
`SKILL.md` (`class MileageKpi: _inherit = ['td.vehicle']` как расширение),
а также фикстура и кейс `who-extends` в `evals/odoo-model-map/` закрепляют
поведение ≤18. Для Odoo 19 это ложный ответ «модуль расширяет td.vehicle»
вместо «создаёт новую модель `mileage.kpi`, копию td.vehicle».

## Проверка

Живого прогона не было: чужой код не запускаем без разрешения, лицензии
нет, исходников Odoo в облаке нет. Проверено чтением кода и сверкой двух
правил с исходниками Odoo 18/19.

| Задача | Без него | С ним |
|---|---|---|
| Найти устаревший API 19 в модуле | зависит от памяти модели; наши чек-листы знают 3 правила | ~15 правил с точной строкой (по коду; не прогоняли) |
| «Кто расширяет td.vehicle» при `_inherit=['td.vehicle']` без `_name` в 19 | `odoo-model-map`: «расширяет» — неверно | «новая модель» — верно (по коду) |

## Что перенести (конкретно)

1. **`boost:odoo-model-map` — исправить** (задача для сессии реализации):
   в `odoo_map.py` различать версию модуля (из `version` манифеста): для 19+
   `_inherit`-список без `_name` → роль «определяет новую модель
   `<имя из класса>`» + предупреждение; поправить пример в `SKILL.md`,
   фикстуру `td_fleet_report/models/kpi.py` (либо `_inherit = 'td.vehicle'`,
   либо явный `_name`) и ожидания кейса `who-extends`; добавить кейс-ловушку
   на этот случай.
2. **`repo-audit/references/odoo-checklist.md`** — блок «Устаревший API
   17–19» из `items/linter-rules.md` (после сверки UNVERIFIED-строк через
   `boost:source-check`) и блок связности: внешний xml-id/модель →
   модуль в `depends`; неимпортированный `.py`; файл не в `data`; кнопка на
   `_`-метод; серьёзность неизвестного поля по месту (`related`/`depends`/
   `_order` — падение установки, `constrains`/`onchange` — лог).
3. **`odoo19-mvp-build:pr-review`** (через `proposals/`) — короткий список
   «v19-ловушек» вместо общей строки «no deprecated v19 API»: `_inherit`
   списком без `_name`, `_inherits` без явного поля, `xpath //tree`,
   `tree_view_ref`, `name_get`, `user_has_groups`, `@api.returns`,
   поля `res.groups` (`group_ids`, `user_ids`, `privilege_id`).
4. **Приём формата**: одна строка «файл:строка — что, с какой версии, на
   что заменить» и понижение серьёзности с пометкой «не проверено», если
   не видна зависимость.

## Риски и заметки

- **Нет лицензии** — нельзя копировать текст/код; установка в организацию
  юридически сомнительна. Можно написать автору.
- Без исходников Odoo нужной версии на диске (наш облачный случай) плагин
  теряет большую часть пользы.
- `pyright-lsp` и `typescript-lsp` перехватывают `.py`/`.js` — конфликт.
- Широкий триггер + хук «используй до grep» меняют поведение Claude во всех
  Odoo-сессиях; при установке это надо измерять.
- Детали: `items/linter-rules.md`, `items/lsp-server.md`, `notes.md`.
