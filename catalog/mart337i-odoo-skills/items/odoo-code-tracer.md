# odoo-code-tracer

- **Путь:** `skills/odoo-code-tracer/SKILL.md` (116 строк)
- **Вердикт:** **адаптировать** — лучшая методическая находка репозитория

## Что это

Трасса выполнения от точки входа: HTTP-маршрут, кнопка, серверное
действие, cron, compute/onchange/constraint, рендер отчёта, вызов из OWL,
вебхук. Шаги: точка входа с файлом и строкой → прямая цепочка вызовов →
наследование и `super()` → неявные триггеры (`depends`, `constrains`,
`onchange`, `ondelete`, переопределения CRUD) → связи в XML → связи во
фронтенде → операции с БД (поиск, запись, SQL, savepoint, блокировки) →
побочные эффекты (чат, письма, активности, вложения, внешние вызовы,
очереди, шина) → проверки прав → выходы. Отдельный блок «Uncertain
paths: что не доказано и какой файл это решит». Таблица «тип входа → где
искать → куда дальше».

## Сравнение с нашим

- `boost:odoo-model-map` отвечает на «кто с кем связан» (структура). Тут
  — «что реально выполнится и с какими побочными эффектами» (поведение).
  Не дублирует, дополняет.
- Блок «Uncertain paths» = наш «Где не искал».
- Слабость: нет инструмента, всё руками; на цепочках `super()` через
  10 модулей модель будет пропускать звенья. `odoo_map.py` уже знает
  `_inherit`, его можно использовать как оглавление для трассы.

## Что взять

Источник: `skills/odoo-code-tracer/SKILL.md@634b2db`. Куда:
`plugins/boost/skills/odoo-model-map/`. Как: пересказ своими словами
(лицензии нет, текст и таблицу не копировать).

Режим «трасса» в `odoo-model-map` (или отдельный узкий скилл
`odoo-trace`): вход — точка входа; сначала карта наследников модели из
`odoo_map.py`, затем цепочка `super()` по порядку загрузки модулей
(`depends`), неявные триггеры, побочные эффекты, права; в конце
«Не доказано». Нужен A/B на 2–3 задачах пилота (например, «что
произойдёт при подтверждении заказа в модуле X»).
