## Как устроен (пересказ)

Шесть шагов, на каждом крупном — одобрение пользователя через
`AskUserQuestion` (по одному вопросу, варианты на выбор):

1. Пересказ требований по функциональным областям; вопросы только там,
   где ответ **изменит решение о границах** (классификация областей,
   команды, стратегия, неясная сила интеграции). Таблица «подобласть /
   ядро-поддерж.-типовая / почему» на подтверждение.
2. Модули, интеграции, таблица оценки каждой связи: сила / расстояние /
   изменчивость / сбалансировано? / действие. Одобрение.
3. На каждый модуль `design.md`: ответственность; **инкапсулированное
   знание** (что знает только он); классификация; контракты интеграций
   (направление, уровень силы, что передаётся, определение границы);
   **векторы изменений** — разумные будущие изменения, которые должны
   затронуть только этот модуль.
4. На каждый модуль `tests.md`: юнит, контрактные, граничные
   (в т.ч. «ничего не протекает»), поведенческие.
5. `architecture.md`: карта, потоки по сценариям, таблица связей,
   решения и компромиссы, неразрешённые риски.
6. **Самоаудит** своего дизайна по правилу баланса с severity
   (критично / существенно / мелко); критичные и существенные —
   исправить и повторить, мелкие — в «риски».

## Сверх нашего (по роли; проверить по тексту `architecture`)

| Идея | Есть ли у нас | Для Odoo |
|---|---|---|
| Классификация областей ТР по изменчивости до нарезки на аддоны | неизвестно | Да: ядро клиента → отдельный аддон с чистыми хуками; справочники/CRUD → можно проще |
| Раздел «инкапсулированное знание» на аддон | неизвестно | Да: какие правила живут только здесь (напр. расчёт скидки ремонта) |
| «Векторы изменений» на аддон | неизвестно | Да, хорошо ложится на ТР формата C (доработки): какая будущая доработка затронет только этот аддон |
| Таблица оценки каждой связи между аддонами | неизвестно (есть таблица трассировки AC — это другое) | Да, со шкалой силы в терминах Odoo (см. `odoo-coupling-lens.md`) |
| Самоаудит дизайна с severity и циклом | неизвестно | Да, дёшево: 1 проход по таблице |
| Тест-спеки по типам, включая контрактные | частично (`testing` в цепочке) | Контрактный тест = тест публичного хука аддона |

## Чего не брать

- Одобрение после каждого шага: у нас ТР уже одобрен клиентом, SPEC
  approved — архитектуре нужен один шлюз, не четыре.
- Свои папки `docs/design/<дата>/` — у нас вывод идёт в SPEC/архитектуру
  цепочки.
- DDD-термины в выводе: в цепочке ТР их не используют.
