# Линза связей для аддонов Odoo (наш набросок)

Это **наша** адаптация идей Balanced Coupling (В. Хононов, coupling.dev,
книга «Balancing Coupling in Software Design») к Odoo. Текст свой, из
`vladikk/modularity` ничего не скопировано (лицензия CC BY-NC-SA 4.0).
Шкалы ниже — наша интерпретация, не авторская; перед вносом в скилл
сверить Odoo-факты по документации 19 (`boost:source-check`).

## Уровень анализа

Смотрим на **аддоны одной базы**. Максимальное расстояние на этом уровне —
граница аддона, а за ней — стандартный модуль Odoo (его «команда» —
Odoo SA, он меняется каждым релизом) и внешняя система.

## Сила интеграции в терминах Odoo (сильная → слабая)

| Уровень | Признаки в коде Odoo |
|---|---|
| Вторжение | Переопределение `_private`-метода чужого аддона без `super()` или с копией его тела; XPath по позиции (`//div[3]`) или по внутренним классам; raw SQL в чужие таблицы; ссылка на внутренний `xml_id` записи чужого аддона; monkeypatch |
| Общее правило | Одно бизнес-правило в двух аддонах (одна формула, одна проверка статуса); переопределение `action_*` с расчётом на порядок вызовов в цепочке `super()` (зависимость от MRO, т.е. от порядка установки) |
| Общая модель | `_inherit` с чтением/записью полей, добавленных другим аддоном; `related` через аддоны; общие `td.*` модели для нескольких аддонов |
| Контракт | Вызов публичного метода, задуманного как точка расширения (`_td_prepare_…` хук), `mail`-сообщения/активности, `ir.config_parameter`, данные через явный сервисный метод; XPath по `name` поля/кнопки |

## Расстояние (малое → большое)

метод в одном файле → модель в одном аддоне → два аддона проекта
(`<project>_<area>`) → аддон проекта ↔ стандартный модуль Odoo/OCA →
↔ внешняя система (API, очередь).
Учитывать: аддоны разных подрядчиков/команд дальше; синхронный вызов
внешней системы в `write`/`create` сцепляет жизненные циклы.

**Связь жизненных циклов** в Odoo явная: `depends`. Всё, что в
`depends`, ставится и обновляется вместе. Лишний `depends` — лишняя
связь без пользы.

## Изменчивость

| Область | Изменчивость | Что из этого следует |
|---|---|---|
| Ядро процесса клиента (то, ради чего ТР) | высокая | Своя модель `td.*`, наружу — только хуки; не размазывать по `_inherit` стандартных моделей |
| Справочники, CRUD, отчёты | низкая | Можно проще, дисбаланс терпим |
| Стандартные модули Odoo | функционально низкая, **реализационно высокая** (каждый мажорный релиз: удалённые поля, переименованные методы, переделанные вью) | Вторжение в стандарт = всегда «изменчиво»; связь со стандартом — только через публичные методы, `super()`, XPath по `name` |

## Правило в одну строку

Сильная связь — в один аддон; между аддонами — контракт; со
стандартом — никогда не вторжение. Слабо связанное в одном аддоне —
резать (одно `<project>_custom` на всё — то же «оба низкие»).

Возможный приём (наша идея, у них нет): если двум аддонам нужно общее
знание, но ни один не должен зависеть от другого — **мост-аддон** с
`depends` на оба и `auto_install: True` (так устроены стандартные
`sale_stock`, `sale_mrp` и др. — сверить по 19.0).

## Пример: пилот `pilot/addons` (ручная оценка, без запуска)

| Связь | Сила | Расстояние | Изменчивость | Баланс | Действие |
|---|---|---|---|---|---|
| `td_workshop_sale` → `td.workshop.order` (`_inherit`, читает `line_ids`, `discount`, `partner_id`) | модель | среднее (аддоны проекта) | высокая (ядро) | терпимо | Достаточно; при росте — хук `_prepare_quotation_vals()` в `td_workshop` |
| `sale.order._prepare_workshop_note()` знает поля заказа ремонта | общее правило, «не на своей модели» | малое (тот же аддон) | средняя | да по модели | Перенести формирование заметки в `td.workshop.order` — знание о ремонте там, где ремонт |
| `td_workshop_sale` → `sale.view_order_form` (XPath по `name="payment_term_id"`) | контракт-ish | большое (стандарт) | реализ. высокая | да | Ок; при апгрейде проверить, что поле осталось во вью |
| `td_workshop_sale` `depends: stock` | — | — | — | лишняя связь жизн. цикла? | Проверить, нужен ли `stock` (в моделях не используется; вью/данные не смотрели) |
| `td_workshop_portal` → `td.workshop.order` через `sudo().browse(id)` | модель + обход прав | среднее | высокая | под вопросом | Это вопрос безопасности, не модульности — к `security-review` |

Вывод примера: линза даёт 1–2 осмысленных замечания на маленьком
проекте, которых `odoo-model-map` (карта) сам по себе не формулирует.
Это **не** A/B: оценку делал я с прочитанной моделью в контексте.

## Куда положить

1. `odoo19-mvp-build:architecture` — раздел «Связи между аддонами»
   (таблица выше) + «Знание аддона» и «Векторы изменений» в карточке
   аддона + один проход самоаудита. Объём ≤ 40 строк в `SKILL.md`,
   шкалы — в `references/coupling-odoo.md`.
2. `boost:odoo-model-map` — необязательный раздел «Оценка связей» в
   формате ответа (только по явной просьбе «оцени связи / модульность»),
   ссылка на тот же `references/coupling-odoo.md`.
3. `odoo19-mvp-build:pr-review` — одна строка чек-листа: «вторжение в
   стандартный модуль (без `super()`, XPath по позиции, SQL в чужие
   таблицы) — находка уровня существенно».
