## Что делает

Учит Claude смотреть на связи между модулями через модель Balanced
Coupling: у каждой связи есть сила (сколько знаний передаётся: от
вторжения во внутренности до явного контракта), расстояние (цена
совместного изменения, включая команды и синхронность) и изменчивость
(по бизнесу, а не по коммитам). Модульно — когда сильное рядом, а далёкое
через контракт; плохо — когда сильное далеко или несвязанное свалено
вместе; низкая изменчивость гасит дисбаланс. `design` из функциональных
требований строит модули, контракты, тест-спеки и сам себя ревьюит;
`review` ищет дисбаланс в готовом коде и пишет отчёт.

**Гипотеза** («проектирование модульной системы из ФТ и ревью
архитектуры») **подтверждена**, с уточнением: это одна модель, а не
общая архитектурная методичка.

## Какую слабость Claude закрывает

**Метод.** Без него Claude рассуждает о связности «на глаз»: одна ось
(число зависимостей), советы «развязать всё», изменчивость по частоте
коммитов. Скилл заставляет:
- оценивать каждую связь по трём осям и записывать это таблицей;
- спрашивать только то, что изменит решение о границах;
- для каждого модуля назвать скрытое в нём знание и будущие изменения,
  которые должны затронуть только его;
- проверить собственный дизайн тем же правилом.

## Как устроен

Только Markdown: 4 `SKILL.md` (~820 строк), HTML-шаблон отчёта (инлайн-JS
для темы, без внешних ресурсов), манифесты плагина и маркетплейса. Нет
скриптов, хуков, MCP, сетевых вызовов. Инструменты: `design` — Read,
Write, Edit, AskUserQuestion, Task*; `review` — Read, Grep, Glob, LSP,
AskUserQuestion, Task*. Вывод в `docs/design/<дата>/` и
`docs/modularity-review/<дата>/` (дата через подстановку `!`date``).
Оба скилла предзагружают справочник модели (~4–5 тыс. токенов) — цена
вызова около 7–8 тыс. токенов до первого действия.

## Сравнение с `odoo19-mvp-build:architecture`

**Ограничение:** текста нашего `architecture` в сессии нет (папка
синхронизированных плагинов пуста). Сравнение по его роли из
`odoo-spec-writer`: получает approved SPEC, делает технический чертёж и
таблицу трассировки AC. Всё «у нас нет» ниже — гипотезы до сверки.

| Что у них | У нас (по роли) | Применимо к аддонам Odoo |
|---|---|---|
| Оценка каждой связи по 3 осям, таблицей | не видно | **Да.** Шкала силы в терминах Odoo: вторжение (`_private` без `super()`, XPath по позиции, SQL в чужие таблицы) → общее правило → общая модель (`_inherit` чужих полей) → контракт (хук-метод) |
| Изменчивость по бизнесу; типовое = стабильная функция, но меняющаяся реализация | не видно | **Да, это самое ценное.** Стандартные модули Odoo функционально стабильны, но реализация меняется каждым релизом → вторжение в стандарт всегда «изменчиво» (наш факт: удалённые в 19.0 поля, `synthesis.md` п.3) |
| «Знание модуля» и «векторы изменений» в карточке модуля | не видно | **Да**, особенно для ТР формата C: какая доработка затронет только этот аддон |
| Самоаудит дизайна с severity и циклом | не видно | **Да**, один проход |
| «Оба низкие» = низкая связность | — | **Да:** против одного `<project>_custom` на всё |
| Расстояние = граница уровня; жизненный цикл | — | **Да:** `depends` = общий цикл установки/обновления; лишний `depends` — лишняя связь |
| Одобрение на каждом из 6 шагов | ТР уже одобрен клиентом | **Нет**, у нас один шлюз |
| DDD-словарь, ссылки на coupling.dev, HTML-отчёт | — | **Нет** |

Чего у них нет и для Odoo нужно: наследование `_inherit`/`_inherits`,
порядок `super()` по порядку установки, XML-наследование вью, права и
`ir.rule` как часть контракта, мост-аддоны с `auto_install`. Это
добавляем сами (`items/odoo-coupling-lens.md`).

## Проверка

A/B не делали: нужен текст нашего `architecture` и разрешение
пользователя. План:

| Задача | Без него | С ним |

| Ревью `pilot/addons` на связи (ключ: `_prepare_workshop_note` не на своей модели, `depends: stock` под вопросом) | `odoo-model-map` | `odoo-model-map` + раздел «Оценка связей» |
| Подложенная ловушка: переопределение стандартного `_private` без `super()` | `pr-review` | `pr-review` + строка чек-листа |

Метрики: нашёл ли ключевые находки, число лишних (принцип «5 важных
лучше 30»), токены. Ручная оценка пилота без A/B — в
`items/odoo-coupling-lens.md`: 1–2 содержательных замечания.
