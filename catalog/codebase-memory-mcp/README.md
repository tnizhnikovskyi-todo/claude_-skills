# codebase-memory-mcp

- **Тип:** MCP-сервер (нативный бинарник на C) + CLI + опционально скилл,
  хуки и UI (CBM Lens)
- **Источник:** https://github.com/DeusData/codebase-memory-mcp
- **Версия / коммит:** `a5b248f` (2026-11-01), последний релиз `v0.12.1`
  (2026-10-16)
- **Дата разбора:** 2026-11-02
- **Вердикт:** **адаптировать**: подключать только MCP-сервер с пином
  версии (вручную в `.mcp.json` или плагином), без `install` (хуки, правка
  конфигов всех агентов). Окончательно после испытания на Odoo-коде.

## Что делает

Индексирует репозиторий в постоянный локальный граф знаний (SQLite в
`~/.cache/codebase-memory-mcp/`) и отдаёт его агенту через 17 MCP-инструментов.
Код разбирается tree-sitter (162 грамматики вшиты в бинарник), поверх него для
11 языков, включая Python, работает «Hybrid LSP»: своя реализация вывода типов
на C, уточняющая, какой метод реально вызывается. Узлы: файлы, классы,
функции, методы, маршруты, ресурсы инфраструктуры (Docker, k8s, Helm,
Terraform), разделы документации. Рёбра: `CALLS`, `IMPORTS`, `INHERITS`,
`OVERRIDE`, `HTTP_CALLS`, `TESTS` и ещё ~35 типов. Запросы: поиск по имени,
BM25 и семантика, трассировка вызовов в обе стороны, Cypher-подмножество,
влияние текущего диффа (`detect_changes`). LLM и сеть для индексации не нужны.

## Какую слабость Claude закрывает

- **Память и контекст.** Claude в каждой сессии заново изучает код grep'ом и
  чтением файлов. Граф живёт между сессиями (на локальной машине) и отвечает
  на «кто вызывает X» компактно, без чтения файлов целиком. Авторы заявляют
  10× меньше токенов и 2,1× меньше вызовов инструментов (препринт
  arXiv 2603.27277, 31 репозиторий, их собственная методика).
- **Знания о структуре.** Цепочки вызовов через несколько файлов, точки
  входа, мёртвый код, влияние изменения на символы и тесты.

### Подключение к Claude Code

Минимально:

```json
{ "mcpServers": { "codebase-memory-mcp": { "command": "/path/to/codebase-memory-mcp", "args": [] } } }
```

Затем в сессии `index_repository(repo_path="/abs/path")` или
`config set auto_index true` (по умолчанию выключено).

### Облачная эфемерная сессия

- Кэш `~/.cache/codebase-memory-mcp/` пропадает вместе с контейнером, значит
  **переиндексация на каждом старте**. По бенчмаркам авторов (Apple M3 Pro):
  Django ~6 с, ядро Linux 3 мин. Кастомные модули Odoo ожидаемо секунды;
  ядро Odoo 19 — оценочно десятки секунд — пара минут на облачном CPU (не
  проверено). Есть `async: true` для долгой индексации и режим `fast`.
- Варианты: (а) `auto_index` при старте MCP; (б) SessionStart-хук с
  `codebase-memory-mcp cli index_repository --repo-path …`; (в) коммитить
  `.codebase-memory/graph.db.zst` и импортировать базу с инкрементальной
  доиндексацией. Вариант (в) раздувает историю git (авторы предупреждают:
  один пользователь получил ~6 ГБ), годится только с редким обновлением.
- Установка бинарника: setup-скриптом из GitHub Releases с проверкой
  SHA-256, либо `npx` (нужен доступ к npm registry и github.com в сетевой
  политике окружения).

### Python и Odoo

- Python в «Good» (75–89%) по их бенчмарку (Django 87%); Hybrid LSP для
  Python: импорты, dataclasses, generics, `@property`, async, narrowing и т.п.
- **Специальной поддержки Odoo нет** (в коде ни одного упоминания).
  Ожидаемо не видит: наследование моделей через строку `_inherit = 'x.y'`,
  `self.env['model']`, связь XML-вью/записей с моделями и полями, ORM-магию.
  Обычные вызовы Python-функций и методов внутри модуля должен видеть.
  Нужна проверка на реальном модуле.

### Сеть, телеметрия, права

- Индексация и запросы локальные. README: «no telemetry», «cbm makes no
  network request of its own accord», фоновой проверки версий нет.
  Грепом по `src/` подтверждено: сокеты только `AF_UNIX` и loopback-HTTP UI;
  внешний трафик только `curl` (без shell, только https) в пути
  установки/обновления.
- Внешние загрузки: бинарник с GitHub Releases (npm/PyPI-обёртки сверяют
  SHA-256 из `checksums.txt` того же релиза); модель для чата в UI с
  Hugging Face только по явному включению.
- Цепочка поставки сильная: SLSA 3, cosign, CodeQL, VirusTotal на каждый
  релиз.
- `git` вызывается через `popen` (история изменений, артефакт).
- `CBM_ALLOWED_ROOT` ограничивает, какие пути можно индексировать.
- `install` пишет в конфиги многих агентов и ставит хуки; `uninstall`
  убирает «свои» записи.

## Сравнение

| | codebase-memory-mcp | graphify (`catalog/graphify/`) | serena (предварительно, карточка в `analysis/serena`) |
|---|---|---|---|
| Ядро | Нативный C, tree-sitter + свой вывод типов | Python, tree-sitter + LLM для документов | Python, настоящие LSP-серверы языков |
| Интерфейс | MCP (17 инстр.) + CLI | CLI + скилл ~10k токенов (+ MCP) | MCP |
| Хранение | SQLite в `~/.cache`, инкрементально, вотчер | `graphify-out/graph.json` в проекте | индекс символов LSP в `.serena/` |
| Сильное | Скорость, трассировка вызовов, `detect_changes`, Cypher, инфраструктура | Документы и картинки в том же графе, метки достоверности | Точные символы по LSP, редактирование по символам |
| Слабое для нас | Нет Odoo-специфики; сложный демон | Тяжёлый скилл, непинованная автоустановка | (по карточке serena) |
| Правка кода | нет | нет | да |
| Сеть | только установка | авто-выбор внешнего LLM по ключам | установка LSP-серверов |

Вывод: из «графовых» инструментов codebase-memory-mcp сильнее graphify как
MCP для кода (быстрее, инкрементальный, меньше контекста, Python с выводом
типов), graphify интереснее для документов. С serena они дополняют друг
друга: граф вызовов и влияние изменений против точной символьной навигации и
правки. Брать оба в облако не стоит, нужно выбрать по испытанию на Odoo.

## Риски и заметки

- Не запускать `install` и скрипты `curl … | bash`: ставить бинарник из
  релиза с проверкой SHA-256 (или cosign) и прописывать MCP вручную.
- Не использовать вместе плагин и `install`: сервер поднимется дважды под
  разными префиксами.
- `auto_watch` по умолчанию включён, в облаке это лишний фоновой процесс;
  можно `watcher_enabled false`.
- Тяжёлый маркетинг в README («99% fewer tokens»): цифры относятся к их
  выборке, на нашем коде проверить.
