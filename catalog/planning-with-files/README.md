# planning-with-files

- **Тип:** плагин Claude Code (1 скилл + 6 хуков + 13 команд) и копии под ~20 других агентов
- **Источник:** https://github.com/OthmanAdi/planning-with-files (★27.9k, MIT)
- **Версия / коммит:** 3.28.0, `0fa6c79885e14534074cb7df8535e1efa3dc7149` (2026-11-03)
- **Лицензия:** MIT (`LICENSE`, Copyright (c) Ahmad Othman Ammar Adi)
- **Дата разбора:** 2026-11-03
- **Вердикт:** **адаптировать** (ставить как есть — нет)

## Что делает

Заставляет агента вести три файла в проекте: `task_plan.md` (цель,
«следующий шаг», фазы `### Phase N` со строкой `**Status:** pending|in_progress|complete`,
решения, таблица ошибок с номером попытки), `findings.md` (находки и
недоверенный внешний материал), `progress.md` (журнал сессии, тесты).
Хуки каждый ход и перед каждым `Read/Grep/Bash/Edit/Write` подмешивают
голову плана в контекст, после `Write/Edit` напоминают обновить прогресс,
на `SessionStart` (в т.ч. после `compact`/`clear`) восстанавливают план,
на `Stop` проверяют, все ли фазы `complete`. Идея — «принцип Manus»:
контекст = RAM, файлы = диск, план надо «рецитировать», чтобы цель не
утонула через 50 вызовов.

## Какую слабость Claude закрывает

1. **Потеря состояния после компакции, `/clear`, падения** в середине
   длинной задачи (не в конце, когда пишется handoff).
2. **Дрейф цели** на длинных задачах: план снова оказывается в конце
   контекста.
3. **Повтор провалившихся действий**: таблица ошибок + «3 попытки, потом
   к пользователю».

## Как устроен

| Часть | Что внутри | Цена |
|---|---|---|
| `skills/planning-with-files/SKILL.md` | 534 строки, 41.8 КБ; фронтматтер с 5 хуками (для установки без плагина) | ≈10–11 тыс. токенов при вызове скилла |
| `hooks/hooks.json` + `hooks/claude-hook.sh` | `SessionStart`, `UserPromptSubmit`, `PreToolUse` (`Write|Edit|Bash|Read|Glob|Grep`), `PostToolUse` (`Write|Edit`), `PreCompact`, `Stop`; таймаут 10 с | по замеру автора ≈330 ток. на ход + ≈90 на вызов инструмента; с v3.24 неизменённый вид не повторяется (нужен приватный кэш `~/.cache/pwf-sha`) |
| `scripts/` | ~12.6 тыс. строк sh/ps1/py: `init-session`, `resolve-plan-dir`, `inject-plan` (sh + py-двойник 1.8 тыс. строк), `check-complete`, `attest-plan` (SHA-256 плана), `ledger-*`, `set-active-plan`, `plan-doctor`, `session-catchup.py` | только по вызову |
| `commands/` | `/plan`, `/plan-goal` (обёртка над `/goal`), `/plan-loop` (над `/loop`), `/plan-attest`, `/plan-doctor`, `/status`, локализации | только по вызову |
| `templates/` | `task_plan.md` (89 строк), `findings.md`, `progress.md`, `loop.md`, аналитический и «автономный» варианты | копируются в проект |
| Режимы v3 | `.mode`: `autonomous` (без инъекций на каждый вызов, сводка JSONL-леджера), `gated` (Stop-хук блокирует остановку, пока есть фаза `in_progress`; кап 20 блоков, детектор застоя) | опционально |
| ~20 папок `.cursor/`, `.codex/`, `.gemini/`, `.kiro/`, … | копии того же скилла/хуков под другие агенты; синхронизируются скриптом | нам не нужны |

**Сеть и телеметрия:** нет. `grep` по `curl|wget|urllib|requests|socket|Invoke-WebRequest`
в `scripts/`, `hooks/` пуст; телеметрии нет. `session-catchup.py` с явным
флагом `--metadata`/`--replay` читает `~/.claude/projects/*.jsonl`
(транскрипты сессий того же проекта) — только по явной просьбе, на
автоматическом пути отключено.

**Права:** `allowed-tools: Read Write Edit Bash Glob Grep`; хуки запускают
`sh`/`python3` из каталога плагина. Ничего не устанавливает глобально,
кроме копирования `loop.md` по инструкции.

**Безопасность по существу:** автор сам описывает главный риск —
усиление prompt injection: всё, что попало в `task_plan.md`, подмешивается
на каждый ход. Защиты: рамки `BEGIN/END PLAN DATA` (с nonce в v3),
правило «внешнее только в `findings.md`», опциональная SHA-аттестация
плана. Сам автор честно пишет, что это не граница доступа.

машинерии; простое правило в `CLAUDE.md` даёт бо́льшую часть эффекта.

| Критерий | Балл (0–3) | Комментарий |

| Частота | 2 | Длинные задачи (сборка MVP, анализ репо) — каждую неделю |

## Сравнение с нашим

| | planning-with-files | `boost:cloud-memory` | `odoo19-mvp-build:build-orchestrator` |
|---|---|---|---|
| Где живёт состояние | `task_plan.md`/`progress.md`/`findings.md` в проекте, **по задумке не коммитится** | `memory/` в git, коммит с ведома пользователя | Список задач в контексте (`TaskCreate`/`TaskUpdate`, по задаче на AC/шаг); файла состояния нет, след остаётся только в коммитах кода |
| Когда пишется | Непрерывно: после каждой фазы, каждые 2 поиска, каждая ошибка | Решения/баги/находки по событию; `HANDOFF.md` — в конце или по просьбе | Отметка задачи после каждого AC |
| Что подмешивается | Голова плана каждый ход и перед инструментами | `INDEX.md` + `HANDOFF.md` один раз на старте (≈9 КБ максимум) | Ничего; после компакции/нового контейнера список задач надо восстанавливать по коду и `ALLOCATION.md` |
| Фазы со статусом и «следующий шаг» | Да, машинно проверяемо (`check-complete`) | Нет (свободный текст handoff) | Шаги фиксированы (scaffold → AC → tests → gate), статус только в списке задач |
| Журнал ошибок с номером попытки | Да | Тупики в handoff | Нет: при красных тестах/`BLOCK` возврат в `code-dev` без лимита попыток и без записи, что пробовали |
| Облако | Файлы теряются с контейнером, если не закоммитить; кэш в `~/.cache` тоже | Рассчитан на облако | Список задач живёт только в сессии |
| Параллельная работа | Один владелец плана, воркеры пишут в свои файлы/леджеры | — | Суборкестратор на модуль (блок B), сводка статусов; общего файла нет |

**Что у них есть сверх нашего:** непрерывный чекпойнт по ходу работы
(спасает при компакции/обрыве посреди задачи), фиксированная структура
фаз с одним статусом, поле «Next Step», таблица ошибок с попытками и
правило «3 попытки → к пользователю», «5 вопросов перезагрузки» как тест
полноты handoff, правило «внешний текст только в `findings.md`, не в
файл, который подмешивается».

**Что хуже:** цена контекста, сложность, файлы не переживают облачный
контейнер по умолчанию, дублирует `TodoWrite`/наш handoff по смыслу.

## Риски и заметки

- **Почему столько звёзд:** ранний (январь 2026) и простой мем «как в
  Manus» с понятной картинкой «до/после `/clear`», поддержка 60+ агентов
  и 5 языков, активный маркетинг README (бейджи, бенчмарки, «Used in the
  Wild»). Сама идея проста; ценность в формате файлов и дисциплине, не в
  коде.
- Бенчмарки — собственные автора; честно оговорены ограничения, но
  заголовочные цифры (96.7%, 3/3) меряют следование формату.
- `gated`-режим (Stop-хук не даёт закончить, пока фаза `in_progress`)
  опасен в облаке без присмотра: до 20 принудительных продолжений.
