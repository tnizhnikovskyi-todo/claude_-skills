# odoo-review и odoo-security (19.0)

- **Тип:** два скилла (по одному `SKILL.md`)
- **Источник:** `odoo/odoo@20.0:skills/` (Odoo S.A., LGPL-3), переработаны
  dooservice под проектный репозиторий
- **Вердикт:** адаптировать в `odoo19-mvp-build:pr-review` и `security-review`

## odoo-review: процесс

1. **Scope**: локальный checkout, пин коммита и базы (`git merge-base`), diff
   только из checkout; исходник Odoo той версии, что у проекта; манифест,
   коммиты, описание PR; отметить, установлен ли модуль в важной БД.
2. **Map**: каждый изменённый файл сопоставить с разделами правил
   (`tests/` → Tests; установленный модуль → «Изменения в установленном модуле»
   и «в стабильной версии»). Файл без раздела = ошибка сопоставления.
3. **Read**: открыть все сопоставленные разделы и таблицу версий до первой находки.
4. **Rules pass**, затем «код, которого diff не показывает»: переопределения
   (`grep "def name("`), переименованные имена в Python/XML/JS, общие контракты
   (контекстные ключи, шаблоны, JS-двойник).
5. **Merits pass**: граничные значения, округление, TZ, пустые и мульти-записи,
   мульти-компания, конкурентность, повторный запуск; совпадает ли текст коммита
   с кодом; упали бы тесты без изменения.
6. **Prove**: `odoo-bin -u <module> --test-enable --stop-after-init`.
7. **Report**: файл:строка, дефект, сценарий отказа, фикс, раздел правил или
   *judgement*; в конце строка «Guidelines read: …».

Сравнение с нашим `pr-review` (оригинал недоступен, есть только реконструкция в
`proposals/odoo19-mvp-build/pr-review/BASELINE-STANDIN.md`): у нас «код против
SPEC/AC» и общее «Odoo conventions». У них нет SPEC, но гораздо точнее «как
не пропустить»: шаги 2, 4, 5 и строка «Guidelines read». Наш INSERT
(4-частная находка, Prove-It) уже близок к шагам 5–7.

**Перенос в `pr-review`:** шаг Map (файл → раздел правил, ничего не оставить без
раздела), блок «код, которого diff не показывает» с тремя grep-ами, Merits pass
с перечнем граничных случаев, строка «прочитанные правила». Своими словами.

## odoo-security: чего нет в нашем `security-review`

Наш (`proposals/odoo19-mvp-build/security-review/current/SKILL.md`): ACL, record rules,
`sudo()`, SQL-инъекции, роуты, секреты, межзаписной доступ, плюс Strix-методология
в предложении. В `odoo-security` дополнительно:

- XSS через `Markup`/`markup()` и экранирование «на входе в DOM»;
- field-level access: `groups=` на поле;
- публичный метод модели = RPC-эндпоинт («по умолчанию приватные `_method`»);
- domain injection (домен из пользовательского ввода);
- `file_open` вместо `open` (path traversal по аддонам);
- `eval` / `safe_eval`;
- не возвращать сложные объекты из методов модели (утечка через RPC);
- `getattr`/`setattr` с пользовательским именем;
- `pickle`; тайминг-атаки (сравнение токенов); мутабельные аргументы по умолчанию.

**Перенос:** эти пункты своими словами в Step B чек-лист `security-review`
(или в `references/` предложения 3.1), атрибуция идеи: Odoo S.A., `odoo/odoo@20.0:skills/odoo-security`.
Методология закрытия (Strix) остаётся нашей: у Odoo её нет.
