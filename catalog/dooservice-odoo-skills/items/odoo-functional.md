# odoo-functional (common)

- **Тип:** скилл (74 файла, ~1 МБ: `SKILL.md`, `method.md`, `connect.md`, 70 рецептов)
- **Источник:** своё у dooservice, общий для 16–20; различия версий внутри рецептов
- **Вердикт:** адаптировать `connect.md` и метод; рецепты как справочник через плагин

## Что делает

Настройка Odoo без модуля, как у функционального консультанта: через ORM-инструменты
среды (MCP), иначе `odoo-bin shell`, иначе внешний API, SQL только на чтение.
Рецепты: бухгалтерия, продажи/CRM, закупки, склад, производство, POS, сайт,
маркетинг, проекты, HR, флот, настройки и безопасность, «почему Odoo делает X».
Каждый рецепт начинается блоком «коротко» (приложения, имена по версиям, разделы),
дальше шаги в порядке меню Odoo и код для каждой версии.

## Метод (10 шагов, суть)

Понять в бизнес-терминах → прочитать текущее состояние → найти рычаг в
`odoo-reference`, а не по памяти → рецепт → предложить изменение, записи и откат,
ждать «да» → менять через ORM мелкими шагами, архивировать, а не удалять →
проверить (перечитать, попробовать от имени пользователя) → заметка об изменении
(что, как откатить, что проверено) → `l10n_*` не покрыт: сказать об этом → нужен
код: предложить ближайшую настройку.

`connect.md`: dry-run = сделать, прочитать, `env.cr.rollback()`, показать,
повторить с `commit()` после согласия; не делать dry-run действий, которые
rollback не отменяет (отправка почты, платёжные/ЭДО-сервисы).

## Для нас

- У нас есть MCP `odoo-connector` с правилами про подтверждение удаления и выбор БД.
  Метод dooservice шире: «прочитай до записи», «заметка с откатом», «архивируй»,
  «dry-run».
- В A/B агенты со скиллом во всех трёх функциональных задачах брали именно этот
  скилл + рецепт + grep по reference. Итог: код только под 19.0, с проверкой
  и откатом.
