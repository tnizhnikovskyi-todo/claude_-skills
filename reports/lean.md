## Eval-кейсы

Фикстуры лежат в `<кейс>/fixture/` и копируются в рабочий каталог прогона
скриптом `<кейс>/setup.sh` (`context.scaffold_script`). Поэтому прогон
требует флага `--scaffold` (скрипты наши, только `cp`). `context.add_dirs`
проверен: агенту каталог не виден, не подходит. Запись файлов в eval-среде
закрыта (Write/Edit требуют операторского `--allow-tools`), поэтому
lean-change-кейсы просят показать изменение диффом в ответе.

### lean-change

| Кейс | Соблазн | Что проверяют грейдеры |
|---|---|---|
| `py-reuse-helper` | «гибко и расширяемо» для `--since` | переиспользован `parse_iso_date`, нет абстракций под будущие фильтры, есть тест, финальная строка риска |
| `odoo-standard` (Odoo 19) | «надёжно пересчитывай сумму и синхронизируй телефон» | `compute`+`@api.depends`+`store=True` без create/write; `related='partner_id.phone'`; `models.Constraint`/`@api.constrains`, не `_sql_constraints`; тест + строка риска |
| `keep-validation` | «упрости, выкинь лишнее» на импорте с валидацией | сохранены обязательные поля, проверка email, транзакция; `normalize_phone` переиспользован; `legacy_mode` удалён с проверкой вызывающих; строка риска |
| `trivial-typo` (негативный) | опечатка | скилл не сработал; дифф только про опечатку |

## Результат A/B

Команда (финальный прогон на итоговых версиях скиллов):

```bash
claude plugin eval plugins/boost --case 'lean-change/*' --runs 3 --max-cost-usd 5 \
  --no-publish --scaffold --trust-plugin -j 4 --threshold 0
claude plugin eval plugins/boost --case 'repo-audit/*' --runs 3 --max-cost-usd 5 \
  --no-publish --scaffold --trust-plugin -j 4 --threshold 0
```

Модель по умолчанию сессии, судья haiku. Оценка = доля пройденных грейдеров
(`tool_used: Skill` — индикатор срабатывания, в оценку не входит).
По 3 прогона на кейс в каждой ветке.

## Что менялось по итогам прогонов

1. **Триггер lean-change.** Первая версия `description` (описание метода)
   срабатывала 1 раз из 9. Переписал как «вызывай ДО того, как писать код,
   если: „гибко“, „расширяемо“, „надёжно“, „упрости“… или доработка модуля
   Odoo». Стало 9/9, на опечатке 0/3.
2. **Шаг «уже есть в репо».** При «упрости» модель с загруженным скиллом
   всё равно ужимала самописную нормализацию телефона в одну строку и не
   искала готовую (0/3). Шаг 2 лестницы и раздел «До правки» теперь требуют
   действия: Grep по теме блока перед тем, как писать или ужимать логику.
   Стало 3/3.
3. **Грейдер `tool_used ... max: 0`** без `min: 0` проверяет диапазон
   `1..0` и всегда падает. В негативных кейсах добавлен `min: 0`.

## Что не получилось / ограничения

- Odoo-кейс `odoo-standard` слабо различает ветки: базовая модель уже
  выбирает `compute`/`related`/`models.Constraint`. Нужна задача потруднее
  (например, с соблазном написать контроллер/JS или cron вместо
  `base.automation`).
- Тест на рискованную логику в Odoo-кейсе со скиллом появляется 1–3 из 3
  прогонов (нестабильно). Можно усилить формулировку для Odoo, но это
  раздует текст; оставил.
- В eval-среде нет записи файлов, поэтому проверяется дифф в ответе, а не
  применённое изменение и не запуск тестов.
- Судья (haiku) не пишет объяснений вердикта; причины провалов смотрел по
  трассам (`--keep-temp`).

## Открытые вопросы

- **Прогон repo-audit на реальном модуле Odoo** (критерий 2.4 «отчёт
  проверен вручную») требует рабочего репозитория из roadmap (строка
  «Рабочий репозиторий для пилота»). Нужен доступ — скажите, какой модуль.
- Включать ли в `lean-change` режим «жёстко» (оспорить требования до
  работы)? Сейчас он только по явной просьбе; с ТР может конфликтовать,
  поэтому в скилле прямо сказано не сокращать объём, зафиксированный в ТР.
- `repo-audit` пересекается с `anthropic-skills:security-review` по части
  безопасности модуля Odoo. Сейчас аудит находит и дыры безопасности, но
  не заменяет security-review перед деплоем.
