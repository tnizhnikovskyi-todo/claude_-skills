# Проверка скиллов (A/B)

Используем встроенную команду Claude Code `claude plugin eval`. Она
прогоняет кейсы с плагином и без него (baseline) и показывает разницу.

```bash
claude plugin eval plugins/boost --case '<скилл>/*' --runs 3 --no-publish
```

Формат кейсов (`case.yaml` или `prompt.md` + `graders/*.md`) смотри в
`claude plugin eval --help` и документации Claude Code (агент
`claude-code-guide`).

## Структура

| Папка | Чья | Что |
|---|---|---|
| `general/` | задача 0.2 | Общий набор реальных задач (код Odoo 19, ТР, дискавери, ревью, исследование, баг). Показывает влияние плагина целиком |
| `<скилл>/` | чат, который делает скилл | Кейсы конкретного скилла: где он должен сработать, где НЕ должен, и что улучшает |
| `results/` | не коммитим | Результаты прогонов (`.gitignore`) |

## Практика `claude plugin eval` (выяснено на первой волне)

- **Имя кейса.** `--case` сравнивается с полем `name`, а не с путём.
  Пиши `name: <скилл>/<кейс>` во frontmatter `prompt.md` / в `case.yaml`.
  Классы символов (`[ab]*`) в фильтре не работают.
- **Инструменты.** Write, Edit, Bash, WebFetch закрыты, пока не дан
  `--allow-tools`. Иначе кейс «не создал файл» проходит из-за окружения.
  Для Bash нужна песочница (`bubblewrap`, `socat`); в облачном образе их
  нет.
- **Фикстуры.** `scaffold_script` лежит внутри папки кейса и запускается
  только с `--scaffold`. `context.add_dirs` агенту не виден.
- **Грейдеры.** В regex нет `(?i)`, нужен `flags: i`; есть
  `match: not_contains`. У `tool_used` с `max: 0` обязательно `min: 0`.
  `match: count:N` не документирован, не используй. У `llm` есть
  `focus: last_message | trace | files | {source: file, path}`; на большом
  trace судья видит только начало, лучше целиться в файл.
- **Судья.** По умолчанию haiku. На длинных русских отчётах с таблицами
  он даёт ложные FAIL: используй `--judge-model sonnet`.
- **Негативный контроль.** Проверяй кейс копией с
  `append_system_prompt` с заведомо плохим поведением: главные грейдеры
  должны упасть.
- **Полезные флаги:** `-j 4`, `--trust-plugin`, `--keep-temp`,
  `--json <файл>`.
- **Многоходовые сценарии** проверяются только через
  `context.history_file` (это `--resume <файл>`). Хватает минимального
  `.jsonl` с репликами user/assistant (`uuid`/`parentUuid`/`sessionId`);
  настоящий транскрипт не коммитить (служебные данные окружения). Кейс с
  историей CLI гоняет в одном плече: базу снимать копией плагина без
  `skills/`. `plugins: []` в кейсе плагин НЕ отключает.
- **Потолок стоимости.** Лимит `--max-cost-usd` считай на ОБА плеча: если
  плечо «с плагином» его съест, базовое плечо молча не запустится (нет
  ключа `without`, при этом `partial: false`), а прогоны, где платные
  грейдеры пропущены по лимиту, получают 0. Такие прогоны не считаются,
  их перезапускают. Пример: `repo-audit/*` ×5 с потолком $6 — у
  `py-service` база успела 1 прогон из 5. Добирать базу копией плагина с
  пустым `skills/` и `--ablation none`, а не всей серией заново.
- **Цена.** Судья sonnet: 4 кейса × 3 прогона × 2 плеча ≈ $5.5. Прогоны с
  историей и субагентами в 3–4 раза дороже обычных.
- **Общая фикстура** для нескольких кейсов: `_fixture/` рядом с кейсами, в
  `setup.sh`: `cp -r "$(dirname "$0")/../_fixture/addons" .`.
- **YAML.** `description` с «: » бери в кавычки.
- **Файл с заранее неизвестным именем** проверяй `tool_used: Write` с
  `input_match` (lookahead); путь привязывай к `"file_path"`, иначе регекс
  ловит упоминание пути в тексте.
- **Фокус судьи на файле с неизвестным именем.** `focus: files` даёт
  судье только список путей, без содержимого; glob в `focus`/`target`
  (`path: "memory/2*.md"`) не работает («does not exist»). Содержимое
  такого файла проверяй `tool_used: Write` с `input_match` по lookahead.
  Регулярки — JS: `\w` и `\b` не видят кириллицу, перечисляй слова.
- **Регулярки на код** пропускают комментарии: `^(?![ \t]*#)…`, `flags: m`.
- **Позитивный контроль** рядом с негативным: подскажи факты в
  `append_system_prompt` и убедись, что 1.0 достижим.
- **`--tag hard`** в `general/` (база 0.74–0.77) для поиска прироста;
  остальное как регрессия; нужен `--allow-tools Write Edit`.
- **Копии истории.** Рядом с `history_file` eval создаёт `<sessionId>.jsonl`
  и папку `<sessionId>/`: добавляй их в `.gitignore` кейса.
- **База для кейсов с историей:** копия плагина без проверяемого скилла и
  его агентов, `--ablation none`, тот же судья.
- **Общий набор `general/`.** Регрессионный уровень (14 кейсов) база
  проходит почти на 1.0. Уровень `hard` (`odoo19-api-traps`,
  `odoo19-sales-traps`) база проходит на 0.755: модель стабильно ошибается
  только на фактах Odoo 19, которых не знает (`partner_id.mobile`,
  `partner_id.title` удалены в 19.0). На нём мерить `source-check` и
  Context7.

## Правила

- **Минимум 3 кейса на скилл:** 2 где он должен помочь, 1 где не должен
  срабатывать (проверка триггера). Для скилла, у которого есть сосед
  (см. «Табло активации»), четвёртый кейс — «задача соседа».
- **Грейдеры проверяют результат, а не слова.** Например: «вопрос задан до
  начала правок», «указан источник с URL», «найдена заложенная ошибка».
- **Без клиентских данных** в кейсах.
- **Отчёт.** Итог прогона (таблица с/без, стоимость, вывод) пишется в
  `reports/<slug>.md` в корне репозитория.
- **Бюджет.** По умолчанию `--runs 3`, `--max-cost-usd 5` на скилл; больше
  только с согласия пользователя.

## Методика A/B (с 2026-11-03)

Источники идей и что откуда — в конце раздела. Всё ниже пересказ своими
словами; числа порогов наши.

### 0. План до прогона (пререгистрация)

Перед первым платным прогоном набора записать в `evals/<скилл>/PLAN.md`
(или в начало отчёта, если прогон разовый):

- **Гипотеза и планка:** что считаем успехом (правило принятия ниже, или
  своё, если строже), какие кейсы решают вердикт.
- **Плечи:** с плагином / без; для правки — старая и новая версия скилла;
  для плагина — leave-one-out. Судья, `--runs`, бюджет на каждое плечо.
- **Стоп-правила:** потолок денег; пилот (1 кейс × 1 прогон) упал по
  окружению → чинить кейс, а не гнать серию; судья проваливает приманку
  → сначала чинить грейдер.
- **Приманки для судьи:** у каждого `llm`-грейдера, решающего вердикт,
  есть негативный контроль (`append_system_prompt` с заведомо плохим
  поведением), на котором он обязан поставить FAIL.

Планку и состав решающих кейсов после первого платного прогона не
меняем. Поменяли — это новый эвал, старые числа в отчёте рядом, с пометкой.

### 1. Четыре вопроса

Набор кейсов скилла отвечает на все четыре. Провал по каждому чинится в
своём месте:

| Вопрос | Чем проверяем | Сигнал провала → что чинить |
|---|---|---|
| **Срабатывает** — вызывается, когда надо, и только тогда | табло активации (`tool_used: Skill`, вне балла), проба «молчания», проба «задача соседа» | не вызвался на своей задаче или вызвался на чужой → `description` |
| **Работает** — после вызова делает дело | грейдеры результата в плече «с плагином» | вызвался, балл низкий → тело `SKILL.md` / `references/` |
| **Окупается** — лучше, чем без него | плечо без плагина, правило принятия | база проходит так же → задача (скилл не нужен или кейс не различает); грейдер неоднозначен → кейс |
| **Держится** — не хуже прошлой версии | парное A/B старой и новой версии, no-regression по кейсам | просел старый кейс → последняя правка |

Отдельный класс — **окружение**: таймаут, лимит API, ошибка судьи,
плагин не отключился в базе, кончился `--max-cost-usd`. Это не сигнал о
скилле (см. «Шум»). В отчёте каждый проваленный кейс относим ровно к
одному классу: `description` / тело / задача / окружение.

### 2. Табло активации

В отчёте отдельной таблицей, не в балле:

| Кейс | Тип | Должен сработать | Сработал (с плагином) |
|---|---|---|---|
| `<скилл>/<кейс>` | свой / молчание / сосед / конкурирующий | да/нет | k/n |

- **Проба «молчания»** — задача рядом по словам, но не по смыслу
  (опечатка, «объясни метод»): скилл НЕ вызывается.
- **Проба «задача соседа»** — задача, которую должен взять соседний скилл
  или встроенная команда (`repo-audit` ↔ `/code-review`, `/security-review`;
  `odoo-model-map` ↔ `odoo19-mvp-build:*`; `skill-feedback` ↔
  `cloud-memory`): наш скилл НЕ вызывается и не пишет свои файлы.
- **Кейс «конкурирующий промпт»** — для скиллов, которые меняют действие
  (не писать в скилл, не коммитить, не сохранять секрет): промпт тянет в
  обратную сторону («быстро, без бюрократии, просто поправь файл»).
  Грейдер ловит именно запрещённое действие (`tool_used … max: 0`), а не
  слова ответа.

### 3. Шум

- **Непригодные прогоны вне знаменателя.** Таймаут, лимит API, ошибка
  судьи, пропуск платных грейдеров по `--max-cost-usd`, плечо не
  запустилось — прогон не считаем ни успехом, ни провалом. Пишем строкой
  «N непригодных (причина)» и перезапускаем только их.
- **Доля, а не pass@k.** Балл кейса — доля пройденных прогонов (или
  средняя доля грейдеров). «Прошёл хотя бы раз» не пишем. Для скиллов из
  задач по расписанию отдельно «прошёл во всех прогонах».
- **Разброс плеча.** Δ кейса, не превышающая разброс баллов внутри плеча
  (max − min по прогонам), считается нулём.
- **Интервал Уилсона (95%)** для доли успехов, пишем рядом с баллом:

  | Успехов | Интервал | Успехов | Интервал |
  |---|---|---|---|
  | 9/9 | 0.70–1.00 | 15/15 | 0.80–1.00 |
  | 8/9 | 0.56–0.98 | 10/15 | 0.42–0.85 |
  | 6/9 | 0.35–0.88 | 25/25 | 0.87–1.00 |
  | 3/9 | 0.12–0.65 | 20/25 | 0.61–0.91 |

  Формула: центр `(p + z²/2n)/(1 + z²/n)`, полуширина
  `z·√(p(1−p)/n + z²/4n²)/(1 + z²/n)`, `z = 1.96`.
- **Минимальный различимый сдвиг.** Грубо `1.96·√(2·p(1−p)/n)` при `n`
  испытаний на плечо. Для 3 кейсов × 3 прогона (`n = 9`): ≈ 0.46 при
  p ≈ 0.5 и ≈ 0.37 при p ≈ 0.8; для 3 × 5 (`n = 15`): 0.36 / 0.29; для 5 × 5
  (`n = 25`): 0.28 / 0.22. Прирост меньше этого порога пишем «в пределах
  шума»; вердикт «взять» на нём одном не строим, а подтверждаем
  `--runs 5` по решающим кейсам (с согласия на бюджет).
- Доля грейдеров внутри прогона (как у нас) не независимые испытания:
  интервал считаем по прогонам (прогон прошёл = все решающие грейдеры PASS),
  среднюю долю грейдеров пишем рядом.

### 4. Контроль

- **Базовое плечо не перезапускаем, пока кейсы те же.** Плечо без плагина
  зависит только от кейса, модели, судьи и версии CLI. Пока они не
  менялись (сверяем по шапке и `git diff` папки кейса), берём сохранённый
  `--json` прошлого прогона. `claude plugin eval` сам так не умеет: гоняем
  `--ablation none` для нового плеча и сравниваем с сохранённым JSON базы.
- Поменяли кейс, грейдер, судью, модель или CLI — база гоняется заново,
  старый JSON не годится.
- **Сохранять JSON** каждого серийного прогона (`--json <файл>`) в
  scratchpad или в `results/` (не коммитится); в отчёте — путь и итог.

### 5. Leave-one-out по плагину

Раз в месяц (или перед поднятием `version` плагина) — вклад каждого
скилла в составе плагина: прогон всего плагина и копии без одного скилла
(`cp -r plugins/boost /tmp/boost-minus-<скилл>` и удалить
`skills/<скилл>`) на `general/` и кейсах соседей, `--ablation none`, тот
же судья. Таблица «скилл | Δ без него | база прошла и без скилла». Скилл,
без которого Δ ≈ 0 два месяца подряд, — кандидат на вывод из плагина
(решает пользователь). Так же видно, не мешает ли скилл соседям.

### 6. Правило принятия

Скилл (или правка) принимается, если по решающим кейсам:

- **Δ > 0.05** (средняя по кейсам) и Δ больше минимального различимого
  сдвига, или подтверждено `--runs 5`; **или**
- **качество то же** (|Δ| ≤ 0.05) **и токенов на прогон на 20% меньше**
  (вход + выход, по `--json`).

Отказ: скилл в 2+ раза дороже без прироста; регресс любого старого кейса
больше разброса плеча (no-regression по каждому кейсу, а не по среднему).

### 7. Шапка отчёта

Перед таблицей с/без в `reports/<slug>.md`:

```markdown
| Окружение | Значение |
|---|---|
| Claude Code | `claude --version` |
| Модель агента / судья | … / sonnet |
| Коммит плагина | `git rev-parse --short HEAD` (и старой версии для парного A/B) |
| Плечи | с плагином / без (`--ablation`) / старая версия / leave-one-out |
| `--runs`, кейсы | 5, `<скилл>/*` |
| Что загрузилось | плагины, MCP, хуки в каждом плече |
| Непригодных прогонов | N (причина) |
| Токены на прогон | вход / выход / кэш |
| Стоимость | $ по плечам и всего |
```

Разные судьи, модели или версии CLI в сравниваемых плечах — сравнение
недействительно.

### 8. Парное A/B правки

Правку скилла сравниваем со старой версией в одной серии, а не с числами
из прошлого отчёта: процедура в
`skills/skill-feedback/references/weekly-review.md` §5.
