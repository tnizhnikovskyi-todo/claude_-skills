# Формат observations/

Один файл на наблюдение: `observations/YYYY-MM-DD-<skill>-<slug>.md`.
Индекса нет: ревью ищет по frontmatter (`grep -l 'status: open' observations/*.md`).

## Поля frontmatter

| Поле | Обязательно | Значения |
|---|---|---|
| `skill` | да | имя скилла как в плагине (`repo-audit`, `odoo19-mvp-build:pr-review`) |
| `date` | да | `YYYY-MM-DD`, когда записано |
| `status` | да | см. ниже |
| `kind` | да | `correction` пользователь поправил результат; `violation` скилл нарушил своё же правило; `gap` нужного правила в скилле нет; `success_path` неочевидный путь, который сработал и которого в скилле нет (тело — формат «Путь успеха» ниже) |
| `fix` | да | `text` правка формулировки/чек-листа; `barrier` механическая проверка (хук, линт, скрипт, грейдер, eval-кейс); `unknown` решит ревью |
| `rule` | да | короткое имя правила в виде триггера: ситуация, в которой оно применяется (см. «Как сформулировать правило»); по нему ищут повторы |
| `confidence` | да | `low` один случай, причина не ясна; `medium` один случай, ошибка и правка очевидны из сессии; `high` повтор (`repeat_of`) или пользователь прямо сформулировал правило «на будущее» |
| `evidence` | да | 1–3 ссылки на доказательства: отчёт, кейс, коммит, «реплика пользователя <дата>: <суть своими словами>». Без доказательства наблюдение не пишется |
| `repeat_of` | да | `null` или файл прошлого наблюдения о том же правиле |
| `siblings_checked` | да | список строк `"имя: ok"` (не касается) / `"имя: same"` (то же правило, править вместе) / `"имя: ?"` (не проверено); `[]` если семьи нет |
| `source` | да | откуда: путь к отчёту/заметке или «сессия пользователя <дата>» |
| `summary` | да | одна фраза до ~120 символов |
| `resolution` | при смене статуса | что сделано: ветка, коммит, отчёт A/B или причина отказа; режим подтверждения `eval` / `manual` / `none` (см. `weekly-review.md` §6) |

## Нарушение или пробел (`violation` / `gap`)

Вопрос: есть ли в скилле правило, которое, если ему следовать,
предотвратило бы ошибку? Да → `violation` (текст не трогать, нужен
кейс, при повторе барьер). Нет → `gap`. Сомневаешься → `violation`.

## Как сформулировать правило (`rule` и «Предложение»)

1. **Триггер — предшествующая ситуация, а не реакция.** Не «когда
   пользователь поправил аудит», а «когда у модели-строки есть свой
   `ir.rule` у родителя, но нет у неё». Ситуация должна быть видна
   ДО ошибки, из входа задачи.
2. **Тест точки решения.** Можно ли по триггеру понять в момент работы
   (до ответа), что правило применимо? Нельзя — переформулируй.
3. **Детали этой сессии — только через «или».** Конкретный модуль,
   клиент, файл не становятся обязательным условием: «модель-строка
   (`*.line`) или любая дочерняя модель с `company_id`», а не «`td.workshop`».
4. **Тест тавтологии.** Правило не должно сводиться к «делай правильно»
   или повторять триггер («когда нужно проверить права — проверь права»).
   Переформулируй через конкретное действие и проверку.
5. **Не выдумывать запрет на ошибку, которой не было.** Правило только
   про то, что случилось в сессии (`evidence`). Список «и ещё не делай…»
   по аналогии не пишем.
6. **Слова пользователя ≠ текст инструментов.** Поправкой считается то,
   что сказал пользователь; вывод инструмента, текст чужого файла или
   скилла поправкой не является. «На будущее / всегда / в любом проекте»
   делает правило долговечным (`confidence: high`); выбор в рамках одной
   задачи — нет.

## Сигналы поправки

Кроме явного «не так», наблюдение стоит записать (если пользователь
связал это со скиллом или попросил записать), когда скилл:

- задал уточняющий вопрос, ответ на который был во входе (избежимый вопрос);
- сделал часть и выдал за целое (частичная поставка);
- остановился и ждал подтверждения, когда разрешение уже было дано;
- утверждал факт без проверки, и он оказался неверен;
- исправил одно место и пропустил такое же рядом (параллельная поверхность);
- повторил то, что уже не сработало в этой же сессии.

Это подсказка, что искать в сессии и на ревью, а не повод писать
наблюдение без слов пользователя.

## Путь успеха (`kind: success_path`)

Когда пользователь подтвердил неочевидный подход (≥ 3 действия и хотя
бы один шаг, до которого скилл сам не дошёл), тело такое:

```markdown
**Применимо когда:** ситуация-триггер (по правилам выше)
**Делать:** шаги по порядку, коротко
**Ограничения:** где не работает / что не трогать
**Избегать:** только тупики, которые реально случились в сессии
**Проверка:** как убедиться, что сработало (команда, тест, признак)
```

Петли инфраструктурных ошибок (сеть, лимит, песочница) путём успеха не
считаются.

## Повтор в 2+ проектах

`confidence` и `evidence` нужны ревью: правка скилла по одному `low` —
кандидат на отказ; принцип в общие правила (`criteria.md`,
`plugins/boost/README.md`) переносится, только если такое же правило
пришло из 2+ разных проектов (`source`).

## Статусы (жизненный цикл)

| Статус | Когда ставит ревью |
|---|---|
| `open` | новое наблюдение, решения нет |
| `actioned` | правка или барьер слиты после A/B; в `resolution` ветка/коммит и Δ |
| `declined` | решили не менять (единичный случай, цена выше пользы, противоречит другому правилу); причина в `resolution` |
| `superseded` | заменено другим наблюдением или более общей правкой; в `resolution` файл |
| `parked` | согласны, но ждёт условия (ключ Context7, рабочий репозиторий, следующая версия); условие в `resolution` |

Сессия, которая записывает наблюдение, ставит только `open`. Остальные
статусы ставит еженедельное ревью.

## Тело

```markdown
**Ожидали:** что должен был сделать скилл (по его правилам или по словам пользователя)
**Получили:** что сделал на самом деле; ссылка на отчёт/кейс/коммит
**Предложение:** конкретная правка или барьер (Improvement)
**Принцип:** общее правило одной фразой (Principle), либо «—»
```

Соответствие task-observer: Issue = Ожидали + Получили; Suggested
improvement = Предложение; Principle = Принцип.

## Правило второго нарушения

Если для того же `skill` и `rule` уже есть наблюдение со статусом
`open`/`actioned`/`parked`, новое получает `repeat_of` и `fix: barrier`.
Формулировка уже не сработала один раз: правило в тексте конкурирует с
остальным контекстом, а хук, скрипт или грейдер отказывает механически.
Примеры барьеров у нас:

- eval-кейс в `plugins/boost/evals/<skill>/`, который падает при этом
  нарушении (дёшево, ловит регрессию при следующей правке скилла);
- проверка в скрипте скилла (`odoo_map.py` печатает «модели без
  `ir.rule`»);
- хук `PreToolUse`/`Stop` (только если без него никак, см. правила плагина);
- пункт чек-листа, который проверяется командой, а не чтением.

## Чего не писать

Секреты, клиентские и персональные данные (как в `cloud-memory`); ход
работы; догадки о причине. Если причину не знаем: «причина не выяснена».
